- **History search is session-scoped (v1.5.0):** MuseDesktop keeps no browsing history between sessions (a privacy choice), so full-text history search covers the current session's page history and window titles only. There is no on-disk history to search, and none is created for this feature.
- **The reading list holds Muse pages only (v1.5.0):** entries are app routes (the R2 AppRoute discipline), so pages on other sites can't be saved, and a restored entry lands on the section, not a scroll position. Signing in is per profile as always: opening another profile's reading entry isn't possible — the list shown is the active profile's.
- **Window groups are forgotten at exit (v1.5.0):** groups-lite name live windows only. For a layout you want back tomorrow, save a workspace (R2) instead.
- **Command schedules run only while the app runs (v1.5.0):** nothing is registered with Windows Task Scheduler. A daily rule whose time passed while MuseDesktop was closed fires once at the next launch; a one-off whose moment passed does the same; neither fires in a burst or retroactively more than once.
- **Focus/session stats measure the timers, not attention (v1.5.0):** focus minutes are the timers' banked minutes — a block that ran while you were away from the PC still counts. The dashboard and digest present them as timer counts, not as proof of concentration.
- **Bandwidth limiting is coarse (v1.4.0):** the pinned WebView2 SDK has no per-transfer throttle, so the limit works by pausing and resuming whole downloads — the AVERAGE rate is capped, the instantaneous speed is not shaped, and a governed download shows as paused while it waits its turn.
- **Held and batched downloads are session-only (v1.4.0):** links held by the download quiet hours and queued batch links live in memory (the S2 retry discipline) — quitting MuseDesktop forgets them rather than writing URLs to disk. A batch link that answers with a web page instead of a file loads invisibly in the hidden view and produces no download, exactly like a retry whose link has gone stale.
- **Middle-click / Ctrl+click audit (v0.5.0, S1 #11):** those gestures reach the app through WebView2's new-window path, exactly like target=_blank, so the existing link policy already governs them (in-app hosts stay, other http(s) goes to the browser, dangerous schemes are blocked). Core tests pin the classification for every host class. No separate handling exists or is needed.

## Behavior

- **The v1.8.4 Setup file cannot close a running MuseDesktop — close it by hand first (fixed in v1.8.5's installer).** The v1.8.4 installer's running-app detection never worked in the field, and a shipped installer can't be fixed retroactively: if you run the v1.8.4 Setup by hand while MuseDesktop is open, quit MuseDesktop yourself first (tray icon → Exit), or the install copies files over the running app. The v1.8.5 installer has no such trap: it detects the running program directly and closes it — including a v1.8.4 copy (handshake if the build knows it, fallbacks otherwise) — before installing.
- **Seamless updates (v1.8.4, R7D) — two honest edges.** (a) **Updating FROM v1.8.3 or older is closed by the installer's fallback, not the handshake.** Those builds don't know `--exit-for-update`: they tolerate the flag and merely wake their window, so the new installer waits, then asks the process to close its main window (a close-to-tray build may hide to the tray instead of exiting), then force-closes it if it still hasn't gone. The update is still fully automatic and the app still relaunches afterwards — the exit is just less gentle that one time. The clean handshake applies from v1.8.4 onward, when both sides speak it. (b) **Rollback keeps the old flow.** Reinstalling the previous version from Diagnostics launches a kept installer that predates this feature: it shows its classic wizard (you click through it), the app exits so setup can take over, and nothing relaunches MuseDesktop afterwards — you start it yourself when the rollback finishes. (The installer detection and relaunch described for v1.8.4 here failed in the field — see the v1.8.4 Setup note above; v1.8.5 rebuilds both, with the relaunch governed by the finish-page Run checkbox.)
- **Token-usage ring (v1.8.2, R7B) — the page may not report usage, and the estimate is rough.** The Muse page may not expose any token or context figure at all; at the time this ships, no usage display is known to exist on the chat page, so ESTIMATE mode is what users should expect to get. The estimate divides the conversation's total text length by a ~4-characters-per-token rule of thumb and measures it against the limit in Settings → Appearance & toolbar (default 200,000 tokens). Real token counts vary with language, code, and formatting, so the estimate can be meaningfully off in either direction — it is a fullness guide, not a meter, and it is never presented as exact: the ring's center shows "~" in estimate mode, and the tooltip and panel say "estimate" outright. If the page ever does display a usage figure (counts or a context percent), the ring adopts it, drops the ~, and labels it page-reported instead. The probe reads only labels the page displays and the conversation's character count — message text is never taken or logged for this feature. The ring tracks the MAIN window's current conversation only.
- **Approval beep (v1.8.3, R7C) — detection depends on the page's approval cards, which can change without notice.** The beep watches the hosted page for an approval card: a visible container holding both an approve-style and a deny-style action button whose whole labels are exactly known words (Allow / Allow once / Allow always / Approve / Yes, with Deny / Reject / Cancel / No). If the page's owner renames those buttons, rebuilds the card, or shows approvals in another language, detection can silently stop — the failure mode is no beep, never a wrong action: the watcher is observe-only and cannot approve, deny, or dismiss anything, whatever it sees. A page dialog that genuinely offers Allow + Deny buttons counts as an approval card for this feature (it is one). The beep fires once per card, only while the MuseDesktop window is not the active window, with a short cooldown between cards; a card that appears while you are already looking at the window never beeps. Turning the sound off is Settings → Tray & notifications → "Beep when an approval needs my attention".
- **Language & announcements (v1.8.0, R7 #161–#170) — scope and limits.** The catalog covers the shell's own windows, menus, dialogs, Settings, tray, and status/announcement lines; the Muse page is never translated. A language change applies to windows opened afterwards; windows already open keep their language until the next launch (the Settings section says so) — rebuilding every open window's text live was rejected as risk without benefit. A few things stay English in every shell language in this version: the Help pages' body text (the Help window's own chrome is translated), the command palette's command titles and details (they come from the Core command registry), guided-test and explainer paragraphs composed in Core, log messages, and the error text the pack validator returns (it is shown verbatim on import, as an API contract). Windows' own dialogs (the file pickers used for pack import/export) follow the Windows display language, not the app's choice. Language packs must be COMPLETE — every string translated — or the import is refused with the reason; partial languages are served by the English fallback of a shipped language, not by half packs. A settings reset does not remove installed packs (they are files in the `language-packs` folder, not settings). Spoken announcements honor the per-type switches for the four automatic kinds; one-off confirmations of something you just did (a test result, "bundle saved") always speak — they are answers, not events — and everything said or muted is recorded in the Diagnostics history either way. Text spacing (#170) is LINE spacing only: WPF exposes no letter-spacing API for its text, so no letter-spacing control is offered rather than a fake one. Right-to-left is readiness only: direction comes from the language itself and windows follow it, proven in tests with a synthetic Arabic pack — but no RTL language ships in this version and RTL layout on a real machine is unverified. The tray menu's TEXT is localized like everything else, but it is drawn by Windows (WinForms) and keeps the system font size, as noted under Appearance (v0.9.0) above.
- **Appearance round 2 (v1.7.0, R6 #151–#160) — scope and limits.** Backdrop materials and the title bar caption tint are Windows 11 DWM features: on Windows 10 (or with Windows transparency effects off, or in High Contrast) both quietly do nothing and the window stays solid with its default caption — there is no simulated substitute. The caption tint colors the whole title bar with the profile color; Windows draws the caption text and buttons over it. The backdrop applies to the main and second windows; dialogs keep the solid face. Compact density changes chrome spacing only (toolbar/status heights and insets) — it never shrinks text or buttons' hit targets below the comfortable layout's glyphs, and it composes with shell text size rather than replacing it. Mini mode is a companion strip, not a small version of the app: it shows the profile color, the current page's favicon and title, and download pause/resume — the page itself stays in the hidden main window (there is no second web view), the strip carries no sign-in or page interaction, entering it is refused while the app is locked, and the app lock closes it along with every other window. Window opacity is per-window, session-only (never saved), bounded at 60%, forced to fully solid in High Contrast and while locked; it is the WPF window opacity, so the whole window including the page area fades together. A custom accent is stored exactly as typed (normalized hex); what paints is a derived pair adjusted in bounded steps until it meets the presets' 4.5:1 contrast contract on both shells — a very light or very saturated pick therefore paints somewhat deeper or brighter than the literal swatch, which is the guard working as intended (the Settings swatch shows the literal color). The theme schedule flips at most once per minute (the existing schedule tick), on this PC's local clock, only while the app runs; Follow Schedule with equal light/dark times means never light. Theme bundles (#160) are not a separate file format: the bundle fields (mode, accent, custom accent, backdrop — plus the schedule times) ride the ordinary settings export/import, and per-profile bundles deliberately do not carry them (they are one global face, not a per-profile one). The mini strip's Pause all / Resume all act through the same tracker as the Downloads window, so WebView2's pause limits (a server without range support may restart a resumed file) apply unchanged.
- **Conversation tools (v1.6.0, R5B #201–#206) — scope and limits.** This slice touches the hosted Muse page (see DECISIONS.md for the scoped exception). The injected script finds messages and the composer by structural markers (message test-ids, `main`/`article` shapes, form heuristics) as of this build: if muse.ai changes its page structure, the affected features quietly stop working rather than breaking the page — the bookmark button may not appear, drafts may stop capturing, export may report it couldn't read the conversation. The custom scrollbar styling targets the page's scroll containers; a page redesign can leave the native (thin, auto-hiding) scrollbar in place until a MuseDesktop update catches up. Export reads the messages the page has loaded/rendered — a very long conversation the page has virtualized may export only its rendered portion. The PDF export prints the conversation PAGE as displayed (Muse's own print rendering), not the tidied Markdown content. Draft send detection is heuristic (Enter, a send-button click, or the composer emptying); an unusual send path can leave a stale draft, which then restores into an empty composer where it can be deleted like any text — drafts never restore over text already in the box. A bookmark's re-find matches the message's stored text snippet: editing (or the page re-rendering) that message can make the find report "couldn't find that message" even though the bookmark and its conversation are intact. Second windows (the S1 optional window) get none of the injections in this slice — conversation tools are a main-window feature for now. Nothing the bridge touches is logged: draft text, snippet bodies, and message text never appear in the app log, by construction (the code paths that handle them have no logging calls).
- **Command palette (v1.1.0, R1 #101–#110) — scope and limits.** Ctrl+K is an in-app binding: like every shell shortcut it reaches the app when the shell has focus; while keyboard focus is inside the Muse page, the page sees the key first (standard WebView2 behavior, the same caveat as F11). The palette searches the shell's own world only — actions, profiles, Settings sections, Help pages, recent downloads, open windows — never page content or conversations, and it injects nothing into muse.ai. Its Recent section remembers built-in action ids only (never a profile, file, or page) in `palette-history.json` beside the settings; deleting that file clears it, and Reset-all-settings deliberately does not (it isn't a preference). Window tiling uses monitor work areas, so a tiled window stops at the taskbar; the switcher's secondary-window titles come from the windows' current page titles, and a secondary window that hasn't finished loading shows its placeholder title. Go-to-profile chords (Ctrl+Shift+1..9) exist only inside the app and only for the first nine profiles — there is no Windows-wide variant by design (see DECISIONS.md).
- **Profiles round 2 (v1.3.0, R3 #121–#130) — scope and limits.** Avatars are text glyphs from the fixed twelve-glyph palette — there are no profile pictures or uploaded images; the desktop-shortcut icon is drawn locally from the glyph + color and refreshes when the shortcut is re-created. A per-profile PIN is the app lock's design and carries its limits exactly (see the App lock entry): it gates launching that profile inside the app and **encrypts nothing**; a forgotten profile PIN has the same settings.json recovery as a forgotten app password, and the global app password is always asked first when both are set. The switching schedule is evaluated only while MuseDesktop is running (once a minute, on this PC's local clock): a window that begins while the app is closed is picked up at the next launch, and a scheduled switch restarts the app like any profile switch. Archiving keeps everything — the data folder, the PIN, and the schedule (paused while archived) — and an archived profile still opens from its own desktop shortcut or link; it is hidden only from switcher surfaces, and the profile in use can't be archived. A profile bundle moves settings + appearance to another PC, never a sign-in: the imported profile starts signed out, and its PIN, schedule, group membership, and usage counts do not travel. Usage counts are tallies kept only on this PC (they ride no export), and deleting them is permanent — there is no other copy.
- **Workspaces & sessions (v1.2.0, R2 #111–#120) — scope and limits.** A workspace remembers an app ROUTE (which Muse section a window shows), never the page's full address: restoring a window lands on that section's current page, not scrolled to where you were, and a conversation whose id lives in a query string is not restored (the route rule strips queries by design — see DECISIONS.md). All windows in this app belong to the one active profile, so a workspace saved from real windows names exactly one profile; applying a workspace of another profile restarts the app into it (after asking), and a hand-edited workspace naming several profiles applies only its own profile's windows and says so in the log. Saved placements are clamped onto the monitors connected at apply time (the S6 #60 rule), so a layout saved on a docked laptop reopens sensibly undocked, not identically. The crash-restore offer appears once per crash and never after a restore that itself died before a page loaded; declining it (or ignoring auto-save being off) loses nothing else — your chats live in Muse, the journal only ever held window sections. Workspaces cap at 16 saved, 12 windows each.
- **No tabs.** Muse's own UI is the tab strip; links that would open a tab follow the link policy (in-app hosts replace the page, everything else goes to your browser). Since v0.5.0 there is a session back/forward history (right-click or long-press Back/Forward) and an optional lightweight second window on the same profile — still no tabs, and the second window has no tray/settings/downloads duties and does not remember its placement (since v1.2.0, workspaces/sessions remember it for it).
- **F11 full screen** is handled by the app window; when keyboard focus is inside the web content, some keys are consumed by the page first (standard WebView2 accelerator behavior). Pages that request full screen themselves (e.g. video) are honored via `ContainsFullScreenElementChanged`.
- **Downloads** run in parallel since v0.6.0 (S2): the status bar shows the single-download wording for one file and an aggregate for several, and the Downloads window's *Active downloads* list manages each one (pause/resume via WebView2 where it reports `CanResume`, cancel, and retry for failures). Status-bar cancel (✕) still acts on the most recent download only. Honest limits that remain: **pause is WebView2's**, so a server without range support may restart a resumed file from zero (WebView2 reports that itself); **retry is this-session only** — download addresses are never stored, so once the app exits a failed download can only be re-downloaded from the chat, and a retry whose link has expired loads invisibly and starts nothing (see DECISIONS.md); **Delete file in the Downloads window is permanent** (it does not use the Recycle Bin) and removes the history entry; the completion balloon is a tray balloon, subject to Windows notification/quiet-hours settings. Files land in your Downloads folder unless a profile override or the shared folder in Settings says otherwise, or ask-where-to-save is on; when the target file already exists the collision setting applies (auto-rename by default).
- **Clearing data** (v0.11.0, S7 #61) lives in Settings → *Privacy & security*: Cookies only / Cache only / All site data, for the current profile or all profiles, each with its consequence stated before confirming. (Before v0.11.0 only an all-or-nothing clear was offered.) A *time-range* clear is not offered — the pinned WebView2 SDK has the overload, but no slice item asked for it.
- **App lock (v0.11.0, S7 #64) — what it is and isn't.** When set, it gates the app's UI (startup prompt before any window exists; Lock now in the tray/⋯ menus; optional lock when the window hides to the tray). **It does not encrypt anything**: profile data on disk is exactly as protected as before (WebView2's own per-Windows-user DPAPI protection), and anyone with access to your Windows account can still read the data folders or simply delete the lock record. It stops casual access to the open app on a shared screen — nothing more, and the Settings text says the same. **Forgotten password:** MuseDesktop stores only a salted one-way hash, so there is nothing to recover the password FROM; the way back in is to quit the app, delete `settings.json` from the data folder (Settings → Data → *Open data folder* shows where; the folder is `%APPDATA%\MuseDesktop` in an installed build), and start the app — the lock is gone and settings return to defaults, including the profile list, but the default profile stays signed in because sign-ins live in the separate profile folders under `%LOCALAPPDATA%\MuseDesktop`. A damaged lock record can never lock you out either: the app detects it at load, turns the lock off, and logs that it did.
- **Permissions manager scope (v0.11.0, S7 #62):** it lists and changes the saved permission choices of the profile MuseDesktop is currently running (the pinned WebView2 SDK enumerates only a live profile's non-default choices — there is no `GetPermissionsAsync` in this SDK version). Another profile's choices are managed by running that profile. The recent-denials list under it covers all profiles on the PC.
- **Certificate errors (v0.11.0, S7 #69):** "Continue anyway" is per site and lasts only until MuseDesktop restarts — there is deliberately no permanent exception list. If the warning dialog can't be shown for any reason, the page is blocked (the safe default) rather than passed silently.
- **Tray suspend:** after a configurable time hidden in the tray (1 / 5 / 15 minutes or never; 5 by default, Settings can also turn suspend off entirely) the web view is suspended to free memory. Suspend never starts during a download, and (v0.8.0) is skipped while a voice session may be live: WebView2 exposes no "microphone is capturing" signal, so the app treats "the microphone was granted to Muse this session" as possibly-live until the page navigates — a deliberately conservative heuristic whose failure mode is saving less memory, never interrupting a call. Its gaps, plainly: a voice session in a launch where the stored permission never re-prompts is not detected by the heuristic (WebView2's own suspend can still decline for live media), and one voice use defers suspend until the next navigation. Suspend is a WebView2 feature — a page in the middle of something can decline it, and streaming replies pause while suspended; everything resumes when you reopen the window.
- **Profiles (v0.3.0):** switching profiles restarts the app (a WebView2 environment is bound to its data folder for the process lifetime). You can't remove the profile you're currently running from Settings. Removing any other profile deletes its data folder right away; if that delete can't happen at the time (folder in use, I/O failure), it is queued and retried automatically at the next launch (v0.7.0) rather than staying on disk. Up to 32 profiles (v0.7.0; adding past 8 asks first). Downloads folder and zoom are shared across profiles by default and can be overridden per profile (v0.6.0/v0.7.0); the sign-in/session data and (since v0.3.1) the restored last page are per-profile. A `--profile <id>` launch (e.g. from a per-profile desktop shortcut, v0.7.0) lands in that profile and makes it the active one. Since v1.0.0 (S11), a second launch while the app is running delivers the switch as a launch intent: the running app asks first (the usual in-app confirm) and restarts into the profile — it never switches silently, and while the app is locked the switch waits behind the lock like every other intent.
- **Installer (v0.3.0):** the NSIS installer is per-user (no admin, no UAC) and unsigned, like the zip — SmartScreen may warn on first run. Installing over an existing install (upgrade) replaces the program files in place; your data folders are never touched by an upgrade. The installer offers a folder choice (reused on upgrade) and an optional desktop shortcut (off by default); since v0.13.0 the shortcut choice is remembered and pre-selected on the next install; since v1.0.0 it also registers the `musedesktop://` scheme per-user, and uninstall removes that registration only while it still points at the install being removed.
- **In-app updates & rollback (v0.13.0, S9 #81/#83/#84/#88):** the updater downloads the new installer and verifies its SHA-256 against the release's `SHA256SUMS.txt` before it can be installed — a release without that file (none of this project's, from v1.0.0 on) is refused by design. **Rollback coverage is a chain, not a time machine:** Diagnostics can reinstall the previous version only when that version's installer was kept by the in-app updater itself, which starts with the first update installed through it; versions installed from the website or the zip have no kept installer, and only ONE previous version is kept. Pre-release channel notes: pre-releases are test builds published on the same Releases page; a stable-channel user is never offered one, and the checker's data comes from the releases list (20 most recent) — a channel with no newer release in that window reads as "up to date".
- **Support bundle & screenshot (v0.14.0, S10 #90/#95):** the bundle is assembled locally and uploaded nowhere — sharing it is the user's act, and the preview + in-zip manifest are the contract for what's inside (bundle settings strip the app-lock record and all full URLs; the log inside is the redacted tail, never the raw file). The optional screenshot captures **only the MuseDesktop window**, rendered from its own visual tree — the desktop and other windows cannot appear — but the page area is rendered exactly as displayed, so **conversation text will be visible in it**; that's why it's opt-in, off by default, shown for review with the warning before it can be included, and not offered at all while the app is locked or the window is hidden.
- **Microphone test (v0.14.0, S10 #92):** the test page is the app's own, served under a reserved host and granted the microphone for that page only inside the test window; it proves the device + Windows permission + WebView2 path work, and reports Muse's saved muse.ai permission alongside — it does not change any permission, and Muse's own voice behavior still depends on muse.ai.
- **Crash recovery (v0.12.0, S8 #71/#76):** automatic recovery happens once per incident — if the recovered page fails again before any page loads successfully, MuseDesktop stops and shows the failure screen rather than looping. Recovery restores the last in-app page; a download in flight when the browser process died is not resumed by recovery (the Downloads window's own retry covers failed downloads, this session only, as before).
- **Data cap (v0.12.0, S8 #75):** the cap counts the whole profile data folder but cleanup can only delete from the explicit cache allowlist — if a profile is over its cap mostly because of non-cache data (site storage, service workers), cleanup frees what it safely can and the folder may stay over the cap; the Settings line and log say what was freed rather than pretending the cap was met. Folder names follow the current Chromium/WebView2 layout; a future layout change makes cleanup a no-op, never a wrong delete.
- **Hung-page watchdog (v0.12.0, S8 #80):** the check is a script ping, so it detects an unresponsive page script engine — a page that is merely slow on the network still answers and is (correctly) left alone. While the page plays audio or the microphone was granted this session the checks pause entirely, so a genuinely hung media page won't raise the banner until playback state changes or the page navigates.
- **Safe mode (v0.12.0, S8 #72):** safe mode changes startup behavior only (Home instead of last page, no automatic update check). It does not disable profiles, the tray, downloads, or the app lock, and it is not a data-repair tool — the guided reset in Settings → Data is the repair path.
- **Global hotkey (v1.0.0, S11 #96):** if another app already owns the chosen combination, Windows refuses the registration — MuseDesktop logs it and Settings → Accessibility & keyboard shows "couldn't register" until a different combination is picked; the feature is off in the meantime, never half-on. The hotkey never hides the window while a modal dialog (Settings, Downloads, a prompt) is open — it only brings the app forward — and while the app is locked it shows the lock screen only. Exiting the app frees the combination for other apps.
- **Quick dictate (v1.0.0, S11 #97):** MuseDesktop can show the window and put keyboard focus inside the Muse page — it cannot press Muse's voice button, move the page's own focus onto the composer, or start a dictation (script injection into muse.ai is a standing refusal). Whether focus then lands somewhere useful is Muse's own keyboard handling. Voice also still needs the microphone granted to Muse: if it isn't, Quick dictate shows the window and a status-line note saying so.
- **Drag & drop (v1.0.0, S11 #98):** file drops onto the Muse page are WebView2's own OLE handling and worked before this version; the shell's drag hint (frame ring + status line) can only appear over the app's own chrome — over the page area the drag belongs to WebView2 and the shell receives no events, so no highlight shows there. The shell never reads dropped files; a drop on the toolbar attaches nothing and says where files belong.
- **musedesktop:// links (v1.0.0, S11 #99):** links work only while the scheme is registered — the installer registers it, and portable installs use the Settings → Behavior toggle. If another app owns the scheme, MuseDesktop reports that in Settings and leaves the other app's registration untouched (turning the toggle off removes only MuseDesktop's own registration). A cold-started link from a browser may show that browser's own "open this app?" prompt first — that's the browser's behavior, not the app's.
- **Notifications** depend on Muse's web app requesting them and on Windows notification settings; the app grants the permission but cannot make Muse use it. MuseDesktop's *own* balloons and its taskbar attention flash additionally honor Windows Do Not Disturb and the in-app quiet-hours schedule (v0.8.0); the Do Not Disturb detection is a best-effort registry read (`NOC_GLOBAL_SETTING_TOASTS_ENABLED`) that does not see Focus Assist's "priority only" mode, and muse.ai's own toasts are not intercepted. The attention badge exists only when Muse's page title uses the "(N)" count convention — the app never guesses a count, so on a title style without it there is simply no badge.
- **Appearance (v0.9.0):** the shell theme and accent color restyle MuseDesktop's own windows only — never the Muse page. "Follow Windows" reads the Windows app-theme preference at startup and when Windows reports a change; a registry read failure means dark (the family default), never a guessed light. Shell text size scales the shell's own text — the **tray menu's font is drawn by Windows and keeps the system size**, and the lightweight second window has no shell text of its own to scale. The toolbar can hide/reorder its buttons, but Back always stays and the ⋯ menu is always last — those two are how you reach everything else, including the setting that would bring the others back.
- **Portable mode (v0.9.0):** with `portable.txt` beside the exe, settings, download history, and logs live in a `data` folder beside the exe — but **sign-in data (the WebView2 profiles) still lives in %LOCALAPPDATA%\MuseDesktop** in this version, so a portable copy does not carry your Muse sign-in with it. Nothing is migrated in either direction: portable launches start fresh, and removing the marker returns to the installed data untouched.
- **Unsigned binary.** SmartScreen will warn on first run until/unless a code-signing certificate is adopted. The signing path is ready (v0.13.0, #87): a manually-triggered workflow exists and stays disabled until the maintainer buys a certificate and adds the two secrets + one variable described in `RELEASE_CHECKLIST.md` — no certificate decision has been made, so this limitation stands.
- **Self-contained download (tens of MB).** Since v0.1.2 the .NET 10 runtime is bundled, so there is no .NET prerequisite — the cost is download size and that runtime patches arrive via app releases rather than the OS. Distribution is an NSIS installer plus a portable zip (since v0.3.0), for x64 and ARM64 (since v0.4.0).
- **ARM64 verification level (v0.4.0):** the ARM64 build is built and smoke-tested (window construction + WebView2 init) on GitHub's real ARM64 Windows runners in CI, but it has not been run on a retail ARM device by the maintainer. The x64 build also runs on Windows-on-ARM under emulation, so ARM users are covered either way; pick the download that matches your PC (Settings → System → About shows the system type). The installers don't block a wrong-architecture install — the file names carry the architecture for that reason.
- **New in v0.4.0, runtime-unverified:** the Downloads window (open / show-in-folder / clear), per-profile start-at-home, settings export/import round-trip, and Ctrl+, for Settings — all on the `RELEASE_CHECKLIST.md` pass list. The v0.4.0 internal refactor (download/tray/update extraction) is covered by the Core suite plus CI smoke; its on-machine behavior folds into the same pass.
- **WebView2 Runtime is a prerequisite** on the minority of Windows 10 PCs that lack it; the app detects this and links to Microsoft's Evergreen installer but does not install it for you.

## Accessibility notes

- **v0.10.0 (S6) did the shell accessibility pass in code:** every shell control carries an accessible name (guarded by an automated XAML audit in the test suite), focus is visibly outlined everywhere via an explicit focus-visual style, Windows High Contrast repaints the shell from system colors, download/update events are announced through UIA live regions, dialogs return focus to their invoker, the web view shows a focus ring while keyboard focus is in the page, and three shortcuts are remappable in Settings. Zoom level is text (not color-only), as before.
- **Still outstanding — machine verification, not code:** a full Narrator pass over the shell and a keyboard-only end-to-end run have NOT been done yet; both are spelled out step-by-step in `RELEASE_CHECKLIST.md` (v0.10.0 section). Until that pass runs, all v0.10.0 accessibility behavior is **Unverified** on a real Windows machine.
- **v1.8.0 (R7) extends the audit and adds the announcement center, in code:** the automated XAML audit now also covers the control types and windows added since round 1 (palette, workspaces, downloads extras, bookmarks + left rail, mini window, R5/R6 surfaces), every interactive control carries an explicit tab index in reading order (pinned by tests), hard-coded user-facing strings fail the build, and spoken announcements have per-type switches plus a written history in Diagnostics. Machine verification (a Narrator pass in English AND Spanish, keyboard-only tab-order walk) is still outstanding — it joins the v0.10.0 items on the `RELEASE_CHECKLIST.md` pass list, and until it runs, all R7 accessibility behavior is **Unverified** on a real Windows machine.
- The tray menu is drawn by Windows (WinForms) and follows the system theme/size; it does not take the shell's theme, text size, or high-contrast palette beyond what Windows itself applies.
