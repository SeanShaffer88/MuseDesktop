# Decisions

A living log of significant architecture, UX, security, and dependency decisions.

## 2026-10-24 — v0.7.0 Slice 3: profiles & accounts (items 23–30)

- **Shortcut mechanism (#23): WScript.Shell late-bound COM, and --profile persists like a switch.** The .lnk is written through `Type.GetTypeFromProgID("WScript.Shell")` + `Activator` (the dynamic COM pattern TaskbarProgress already uses), not IShellLink P/Invoke — a dozen lines, no vtable declarations to get wrong, failure-tolerant with a plain error in Settings. Arguments are parsed by a new Core `CommandLine` parser (the start of item 100's CLI surface: --background, --smoke-test, --profile in both `--profile x` and `--profile=x` forms; unknown args collected, never fatal). Semantics: **--profile makes that profile the active one for the launch AND persists it**, because that is exactly what the existing switch flow does (persist ActiveProfileId, restart) — the last-used profile is what plain launches reopen, and a shortcut that behaved differently from a switch would be the surprising option. Invalid/unknown ids fall back to the saved active profile with a log line. Stated limit: while the app is already running, single-instance still just wakes the running window — a shortcut does not switch a running instance.
- **Zoom-write rule (#26): an override owns in-app zoom changes.** Effective zoom = the active profile's override when set, else the shared zoom (Core `Profiles.EffectiveZoom`, clamped via ZoomMath). While an override exists, zoom gestures (Ctrl +/−/0, toolbar, page zoom control) persist to the override (via `PersistZoom` at save points) and the shared zoom is not touched; the Settings shared-zoom field likewise applies only to profiles without an override. Turning the override off returns the profile to the shared zoom at its current value. This keeps "my Work profile is at 125%" from drifting the shared default every other profile uses.
- **Deferred folder deletion (#28): a persisted id queue, retried pre-environment.** Settings stores `PendingProfileFolderDeletions`. Removal still deletes immediately when it can; the running profile's folder and failed deletes are queued instead (previously: the folder stayed forever, per the old KNOWN_LIMITATIONS). At startup — after the single-instance check, before the main window exists, hence before any WebView2 environment can hold a folder open — each queued folder delete is retried, never for the profile being launched. Sanitization is the safety net: the list is deduped, valid ids only, capped, and **any id naming a live profile is dropped**, so a re-created profile can never have its folder deleted out from under it.
- **Profile cap (#30): 32 hard, 8 soft.** `Profiles.MaxProfiles` 8 → 32 (EnsureValid truncates deterministically from the tail, as before). The old 8 becomes `SoftProfileWarningThreshold`: the Settings Add flow confirms past it, because the real cost of many profiles is disk (a full WebView2 data folder each), not correctness.
- **Copy-settings is a Core whitelist (#29).** `Profiles.CopySettingsFrom` copies exactly StartAtHome, DownloadsFolder, ZoomFactor, DisplayColor into a fresh id/name. Everything session-adjacent is excluded by construction: LastUsedUtc starts null, and last pages live in `LastUrlByProfile` under the profile's own id, so a new id has none. Tests pin both directions.
- **Colors are a fixed palette of keys (#24),** stored as names ("Blue"), painted from Core hex values. Unknown keys sanitize to none, so settings files can't invent colors and the palette can evolve without breaking old files. Dots are real UI (colored ellipse in WPF, generated swatch image in the WinForms tray menu, "●" glyph in text-only surfaces like the tooltip), accents only — the family black/red look is unchanged.

## 2026-10-24 — v0.6.0 Slice 2: downloads (items 13–22)

- **Pause/resume API finding (#14): PRESENT in the pinned SDK, no fallback or fake needed.** The 1.0.4258.31 package's Core XML documents `CoreWebView2DownloadOperation.Pause()`, `.Resume()`, and `.CanResume`, plus the `UserPaused` interrupt reason. Semantics that shaped the tracker: pausing moves the operation to `Interrupted` with reason `UserPaused` — so "interrupted" is not synonymous with "failed". The tracker treats `UserPaused` as a first-class Paused state (stays tracked, no history record, Resume offered per `CanResume`), `UserCanceled` as cancelled (no record), and every other interrupt reason as a failure. (The SDK's own Pause summary text says "UserCanceled" — that contradicts its `UserPaused` enum member and the documented resume flow; the enum is what the code keys on, and the S2 on-machine pass must confirm the reason value in practice.)
- **Retry mechanism (#15): a hidden WebView2 on the same environment, in-session only — and why nothing stronger exists.** Download source URLs are never persisted (standing rule), so after a failure the URI survives only in the shell's memory (`SessionFailedDownload`). Retry creates a 1×1 hidden WebView2 from the main window's existing `CoreWebView2Environment` (same profile/sign-in), wires its `DownloadStarting` to the *same* handler the main view uses — so destination policy (effective folder, ask-where-to-save, collision handling) is identical — and navigates it to the remembered URI. If the server answers with a file, the handler takes the operation over and the tracker follows it like any download. Honest limits: if the server instead returns a page (expired signed link, interstitial), that page loads invisibly in the hidden view and no download starts — a manual re-download from the chat is then the route, and the status bar says the retry was started, never that it succeeded. There is no WebView2 "restart this operation from a URL" API; re-navigation is the only real mechanism, and fabricating a resume of the dead operation was rejected.
- **Failure records in history (#16): a State field, defaulting to Completed.** Old history files have no state field and deserialize as Completed — which is exactly what every pre-v0.6.0 record was. Failed records store the interrupt-reason *name* (e.g. `NetworkFailed`), size-received, and time; never a URL. User-cancelled downloads are deliberately NOT recorded: the user already knows they cancelled, and a history full of cancellations would drown the failures the filter exists to find.
- **The multi-download manager lives in the existing Downloads window (#13),** not a new window or popover: an Active list on top (polled at 750 ms while open, selection preserved by id) over the history list. The status bar keeps the pre-S2 `ProgressStatus` wording byte-for-byte for a single download — the only intentional wording change in the slice is the speed appended to the right-hand detail (#22), implemented as a new overload so the pinned v0.4.0 tests pass unmodified. With several downloads the status bar switches to a Core-computed aggregate; per-file detail lives in the manager.
- **Taskbar progress (#19): ITaskbarList3 via a vtable-prefix interface.** Only the interface prefix through `SetProgressState` is declared (COM slots are positional), the coclass is activated through `Type.GetTypeFromCLSID` + `Activator` (a direct cast from a ComImport coclass doesn't compile), and every call is wrapped so a taskbar failure degrades to a log line. Failure latches the Error state in the main window until the next download starts; a paused-only set shows Paused (yellow).
- **Effective downloads folder (#20) is a Core resolution, not shell branching:** profile override ?? shared folder ?? null, where null deliberately means "leave `ResultFilePath` at WebView2's default" — that's the *system* Downloads folder including when a user has relocated it in Windows, which a hard-coded `%USERPROFILE%\Downloads` would get wrong.
- **Delete-file removes the history entry too (#17).** The alternative (keep a row pointing at a file the user just deleted from inside this window) was rejected as a confusion factory; Clear-history remains the files-untouched route. The confirm dialog states plainly that `File.Delete` is permanent (no Recycle Bin) — if a future slice wants bin semantics it will need a shell API this one deliberately did not fake.

## 2026-10-24 — v0.5.0 Slice 1: window & navigation (items 1–12)

- **Find API availability (#1): verified present in the pinned SDK.** The 1.0.4258.31 package's Core XML documents `CoreWebView2.Find` (`CoreWebView2Find.StartAsync/FindNext/FindPrevious/Stop`, `MatchCount`, `ActiveMatchIndex`, `MatchCountChanged`/`ActiveMatchIndexChanged`, `CoreWebView2Environment.CreateFindOptions`). No fallback was needed and no SDK bump was made. The shell builds its own small find bar (WebView2's default find dialog is suppressed via `SuppressDefaultFindDialog`) so the UI matches the app and Esc handling stays ours.
- **Second window route (#7): same-environment secondary window, NOT a second process.** A `SecondaryWindow` hosts a WebView2 created from the main window's existing `CoreWebView2Environment`, so it shares the active profile's sign-in and user-data folder with no second folder lock, no single-instance exception, and no `--new-window` process flag. Trade-offs, stated plainly: the secondary window is deliberately lightweight (no tray/settings/downloads/update duties, no placement persistence, its own new-window requests follow UrlPolicy), two renderers on one profile cost more memory, and closing the main window (real Exit) still ends the app including secondary windows. The process-flag alternative was rejected because a second process cannot open the same WebView2 user-data folder while the first holds it.
- **Per-profile placement migration (#8): additive, not a replacement.** Settings gain `WindowPlacementByProfile`; `Sanitized()` migrates the legacy global Window* fields into the default profile's entry on first load and drops entries for deleted profiles. The shell reads/writes only the active profile's entry, and `SetActivePlacement` mirrors the active values back into the legacy global fields so a downgrade to v0.4.0 still restores a sensible placement. Sizes are clamped to the same ranges as the global fields.
- **Load-failure classification lives in Core as strings (#10).** `LoadFailureClassifier` takes the `CoreWebView2WebErrorStatus` name as a string, keeping Core free of the WebView2 SDK (the repo's standing layering rule). Auto-retry is exactly once per failure episode: a flag set on retry, cleared on the next successful navigation, triggered only by `NetworkChange.NetworkAddressChanged` with connectivity reported back and the failure overlay visible — a flapping network cannot loop it.
- **Focus mode key: F8 (#6).** Chosen over Ctrl+Shift+F: a single memorable key that pairs with F11, with no chord to conflict with page shortcuts; Esc also exits. Focus mode is session-only and composes with full screen (exiting full screen respects an active focus mode).
- **History model is session-only (#3, #9).** `NavigationHistory` is not persisted: it exists for the Back/Forward dropdowns and Ctrl+Shift+T within a session. Jumping from a dropdown navigates the WebView2 to the entry's URL (WebView2 keeps its own stack; the model pointer is advisory), which is the only jump mechanism WebView2 offers — there is no back-list enumeration or indexed-go API.

## 2026-10-23 — v0.4.0: ARM64 builds, main-window decomposition, download history

- **ARM64 ships as a first-class build.** GitHub's `windows-11-arm` hosted runners are GA and free for public repos, so the ARM64 artifact is built *and* smoke-tested (window + WebView2 init) on real ARM64 hardware in CI — the earlier "no ARM runner" blocker no longer exists. The honest limit stands in KNOWN_LIMITATIONS: CI-verified, no retail-device field test. The x64 build already ran on Windows-on-ARM under emulation; native ARM64 is a performance/battery improvement, not a compatibility rescue. Installers stay per-architecture files with the arch in the name rather than one universal installer — two small files beat NSIS-time arch detection complexity.
- **MainWindow decomposition, along feature seams.** `MainWindow.xaml.cs` (1,064 lines) shed download tracking (`DownloadTracker`), the tray + suspend timer (`TrayController`), and the update check (`UpdateService`); the download status wording moved to Core (`DownloadText`) for unit tests. This executes the 2026-10-21 decision that extraction rides along with features rather than landing as a standalone refactor. Two micro-fixes rode along deliberately: tray *Reload* no-ops before the web view is ready (previously it could throw), and Settings adoption now includes `LastUrlByProfile` (imports carry per-profile start pages). The old no-op `UpdateTrayMenuState` hook was dropped — the tray menu has no dynamic state.
- **Download history is a separate small store** (`downloads.json`, newest-first, capped at 50), not a settings field: it changes on every download, and settings are user configuration worth keeping stable and exportable. Records hold name/path/size/time — never the source URL (the app's log-redaction rule applied to persisted data).
- **Start-page choice lives on the profile** (`AccountProfile.StartAtHome`), because what "start" means follows the sign-in, like the last page itself. Settings export/import reuses the app's own JSON format and `Sanitized()` validation; sign-ins are never exported (they are WebView2 profile data, not settings).
- **Keyboard audit result:** the gesture set (Ctrl+R/F5, Ctrl+±/0, Alt+←/→, F11) already existed with toolbar tooltips and a README table. v0.4.0 adds only Ctrl+, (the Windows Settings convention) plus its ⋯-menu gesture label; no other keyboard work was warranted.

## 2026-10-23 — Per-profile last page; single-file publishing measured and rejected (v0.3.1)

- **Last page is per-profile state, not app state.** v0.3.0's profiles shared `LastUrl`, leaking one account's last chat into another account's launch. Session state follows the profile (like cookies do); preferences (zoom, downloads) stay shared. Migration is one-way and lossless: the legacy value becomes the default profile's entry in `Sanitized()`, so no downgrade/upgrade dance can resurrect the leak.
- **Single-file publish: rejected on measurement.** `PublishSingleFile + EnableCompressionInSingleFile` produces a 69.8 MB exe vs the 70.3 MB folder zip — the "saving" is rounding error, and it buys temp-extraction on every launch plus a WebView2Loader resolution risk we can't runtime-test from the build VM. Revisit only if the runtime payload shrinks materially (e.g. a future .NET trimming story for WPF).

## 2026-10-23 — v0.3.0: account profiles, and an NSIS installer built from the verified artifact

SEAN directed: implement the remaining improvements, and include installers on the next publish.

- **Profiles = separate WebView2 user-data folders**, the only real isolation the platform offers (a folder is a whole browser profile: cookies, storage, cache). The default profile keeps the historic `WebView2` folder — renaming it would sign every existing user out, so the folder scheme is `WebView2` + `WebView2-<id>` siblings. Switching profiles restarts the app (an environment is bound to its folder per process); the relaunch is a detached `cmd` delayed-start after this process exits and frees the single-instance mutex. Profile list invariants are enforced in Core on every load (`Profiles.EnsureValid`), so a hand-edited settings file can't strand the app.
- **Installer = NSIS, built from the hash-verified CI artifact** (script in `installer/MuseDesktop.nsi`, compiled with makensis at release time from the exact bytes CI produced and this release process hash-checked — the installer never carries separately-built binaries). NSIS over Inno Setup/MSIX because: it compiles cross-platform in the release pipeline, per-user install needs no admin and no signing (MSIX would force the signing question SEAN has ruled out unless required), and SEAN's other projects already use NSIS. **Per-user** install (`%LOCALAPPDATA%\Programs\MuseDesktop`, HKCU uninstall key) matches the app's all-per-user data layout. The uninstaller preserves user data by default with an explicit opt-in delete — the zip flow's behavior, carried into the installer.
- **Satellite trim:** `SatelliteResourceLanguages=en` — honest small win; full trimming is not safe for WPF and ReadyToRun costs more size than it saves users.

## 2026-10-23 — The v0.2.0 pack: Settings window, update check, download controls, clear data, tray suspend

SEAN picked the full v0.2.0 bundle from the improvement shortlist. Decisions inside it:

- **Update channel = GitHub Releases.** The public repo's `/releases/latest` endpoint is the single source of truth; the app compares its assembly version against the tag (Core `UpdateInfo`, unit-tested). One request per launch, 12 s timeout, User-Agent identifies the app; every failure path is a log line, never UI. Pre-release tags never count as updates. No third-party updater framework — at this app's scale a notifier + link is honest and sufficient, and auto-install would need signing/update plumbing deliberately out of scope.
- **Settings window edits a clone** (`AppSettings.Clone()`), OK adopts, Cancel discards — the forgiving-UI standard. The ⋯ menu's checkable toggles were removed so settings have exactly one home; the menu keeps actions (Settings…, Check for updates, log folder, About).
- **Clear data uses the WebView2 profile API** (`Profile.ClearBrowsingDataAsync(All)`) rather than deleting the profile folder: the folder delete races the running controller and can't happen in-process; the API is the platform's supported reset and keeps the profile structure intact.
- **Suspend uses WebView2's own `TrySuspendAsync`** after 5 minutes hidden (not a process freeze): the platform knows how to sleep a renderer safely and resume it; the app honors a decline, never suspends mid-download, and resumes before showing the window.
- **Downloads stay single-operation in the status bar** (see KNOWN_LIMITATIONS) but gained the controls users actually reach for: cancel, click-to-open, folder choice, Save-As. A multi-download manager UI stays deferred until there's evidence one download at a time hurts.

## 2026-10-23 — Close minimizes to tray by default (v0.1.3)

v0.1.2 passed its on-machine verification (clean startup log, sign-in and voice confirmed by SEAN). His direction from that session: **closing the window minimizes to the tray by default** — MuseDesktop is a resident companion app, so the X means "put it away," and Exit lives on the tray menu where it always has. The default applies to fresh installs; existing installs keep their saved preference (settings are per-user and the ⋯ toggle is one click). If real-world feedback says the default confuses people, it's a one-line change in `AppSettings`.

## 2026-10-21 — Public product; .NET 10; self-contained download (v0.1.2)

SEAN set the audience to **public product** (not personal tool) and approved the review's top recommendations. Consequences:

- **.NET 8 → .NET 10 LTS.** Microsoft ends .NET 8 support on 2026-11-10; an app that hosts a browser and holds a signed-in session must not sit on an unpatched runtime. .NET 10 LTS runs to November 2028. `global.json` pins the SDK band (10.0.x, latestFeature) so builds are reproducible.
- **Self-contained publish replaces framework-dependent.** A public first-run cannot dead-end on a missing .NET Desktop Runtime with a generic OS dialog. The zip grows from ~0.7 MB to tens of MB (the publish folder measures 175 MB before compression); in exchange the only remaining prerequisite is the WebView2 Runtime, which the app already detects with a guided path. Trade-off accepted knowingly: the bundled runtime is patched by shipping new app releases rather than by the OS, which makes keeping releases current part of the deal.
- **DevTools is Debug-only** — a release build should not hand a scripting console to a signed-in session.
- **Runtime verification is a release gate, not a hope:** the CI smoke test now requires WebView2 to initialize, and `RELEASE_CHECKLIST.md` defines the on-machine checks. This is the structural answer to the v0.1.0 startup crash, which every compile/test check missed.

## 2026-10-20 — C# / WPF + WebView2 instead of the usual Rust default

Muse is a website, so the client is a shell around a web view. On Windows the first-party tool for that is Microsoft's WebView2 (Edge/Chromium) with its official .NET SDK: documented APIs for the exact things this app needs — a persistent user-data folder (login session), new-window and navigation events, permission requests, and download operations with progress and ETA.

The Rust alternative (wry/tao) abstracts those away behind a cross-platform API whose surface changes noticeably between minor versions, and exposes downloads/permissions only partially. The concrete advantage — a stable, Microsoft-maintained SDK for the one platform this app targets — outweighs the standing Rust default for this project. Plain logic (URL policy, settings, zoom) lives in a dependency-free `MuseDesktop.Core` library so it stays unit-testable anywhere, and the WPF shell stays thin.

Alternatives considered: Tauri (Rust + WebView2, but a large toolchain/JS build for a single-window shell); Electron (bundles a whole Chromium — hundreds of MB to show one website, and a second browser profile to secure); a PWA shortcut (no tray, no download progress, no link policy — the behaviors that justify a native client at all).

## 2026-10-20 — Framework-dependent publish, Evergreen WebView2

The release is a framework-dependent win-x64 publish (~a few MB) that requires the .NET 8 Desktop Runtime and the Evergreen WebView2 Runtime (preinstalled on Windows 11 / most Windows 10). This keeps downloads small and lets Microsoft service the web engine's security fixes independently of this app. Trade-off: two runtime prerequisites, both detected with a plain-language explanation in-app when missing (WebView2) or by Windows itself (.NET).

## 2026-10-20 — Link and permission policy

- Top-level navigation: any HTTPS page may load (sign-in and connector OAuth flows redirect across providers). HTTP and non-web schemes are refused.
- New-window requests: only Muse and known identity-provider hosts (`muse.ai`, `meta.com`, `facebook.com`, `instagram.com`, `accounts.google.com`, `appleid.apple.com`, `login.microsoftonline.com`, exact host or true subdomain) stay in-app. All other http(s) links open in the user's default browser. Look-alike hosts never match.
- Permissions: auto-grant only `notifications` and `microphone`, only for origin `https://muse.ai`. Everything else is denied and logged. Rationale: notifications are how a long-running agent says "done", and the microphone is Muse's voice input; a desktop client that silently granted camera/geolocation to arbitrary origins would be a liability.

## 2026-10-20 — Downloads handled in the status bar

WebView2's default download flyout is suppressed (`DownloadStarting` → `Handled`) and progress is reported in the app status bar as percent + ETA from the download operation, because that matches how the rest of SEAN's apps report progress and keeps the single-window app self-contained. Files land in the default Downloads folder (WebView2's default path).

## 2026-10-20 — Black/red product-family look

Toolbar and status bar use the family tokens (near-black surfaces `#0B0B0D`/`#141417`, hairline `#2C2C31`, red accent `#E50914`, off-white text), and the Windows title bar is set to immersive dark via `DwmSetWindowAttribute`. The web content itself is Muse's own design and is not restyled — injecting CSS into a third-party app would break with their updates and misrepresent their product.

## 2026-10-20 — Settings format

One JSON file, schema-versioned, written atomically (temp file + replace). A file that fails to parse is copied aside as `settings.json.corrupt-<timestamp>` and defaults are used, so user data is never silently discarded. The WebView2 bootstrapper link used in the missing-runtime message is Microsoft's official fwlink (`https://go.microsoft.com/fwlink/p/?LinkId=2124703`, the Evergreen bootstrapper referenced in Microsoft's WebView2 distribution docs).
