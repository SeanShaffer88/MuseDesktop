# Decisions

A living log of significant architecture, UX, security, and dependency decisions.

## 2026-10-25 — v1.6.0 Round 2 Slice R5B: conversation tools (items 201–206)

- **The no-injection rule gains a scoped, owner-approved exception.** The standing rule (2026-10-20) was that the shell never restyles or injects into muse.ai. SEAN's follow-on six require exactly that, so this slice injects — and the exception is drawn tightly: the app may RESTYLE the page at the user's own settings (scrollbars, text size, column width, line spacing), OBSERVE it (composer text for drafts, message structure for export/find), and INSERT text the user explicitly chose (a snippet, a restored draft) into the composer. It never acts in the page on the user's behalf: nothing is sent, submitted, clicked, or navigated by injection. All of it ships as one document script installed with `AddScriptToExecuteOnDocumentCreatedAsync`, and every feature degrades to a quiet no-op if the page's shape changes — the page as shipped is always the fallback. This entry does not reopen the rule for anything beyond these six items.
- **The left rail is new chrome, because there was none (#202).** SEAN's design puts the Bookmarks button on "the left vertical toolbar" — the shell had no left rail (its chrome is the top toolbar, find bar, and status bar), so R5B adds a minimal 44px rail holding the one button SEAN named. It is not a general navigation strip: future buttons need their own decision, exactly as the ⋯ menu grew item by item.
- **The nickname rule is enforced in Core, on every path (#202).** `MessageBookmarks.Add` refuses a blank nickname, `Rename` refuses one, and loading drops nickname-less entries — so no route (the prompt loop, a hand-edited file, a future importer) can produce an unnamed bookmark. The prompt loops until a name is given or the user cancels; there is no "save anyway". The bookmark stores the conversation ROUTE plus a plain-text snippet of the message (280 chars) for the re-find — never a URL, never page HTML.
- **Draft send detection is a heuristic, stated as one (#204).** Nothing in the hosted page announces "sent". The bridge treats an Enter keydown, a send-button click, or the composer emptying to nothing as the end of a draft and clears it; ordinary edits keep it. A missed clear costs one stale draft restored into an empty composer (deletable by selecting-all and typing); a missed capture costs nothing — the text was never the app's to guarantee. Draft text is never logged, on any path, including failures.
- **PDF export prints the page as displayed (#203).** The pinned SDK's `PrintToPdfAsync` prints the live page — the conversation as the user sees it — rather than a re-rendered document built from the Markdown extraction. Markdown is the tidy, portable form; PDF is the faithful picture. Building a second print pipeline to force the extraction into print was rejected: two renderings of one conversation would drift, and the honest label is in the UI copy and KNOWN_LIMITATIONS.
- **The new stores extend the R2/R5 file discipline.** `bookmarks.json`, `drafts.json`, `snippets.json` sit beside settings.json, one file per concern, Core-owned, corruption-tolerant (a malformed entry is dropped at load, never fatal), capped (200/50/100 per profile), and — like the reading list — they never ride a settings export; profile bundles carry only the four new APPEARANCE fields, which join the bundle's field-by-field carried copy in BOTH directions (Export's rebuild and TryImport's rebuild — the bundle type copies by hand, so a field added to one side only would silently vanish; a test pins all four).

## 2026-10-25 — v1.5.0 Round 2 Slice R5: focus & productivity (items 141–150)

- **Both timers are Core state machines on the AppLockThrottle pattern (#141/#142).** Every method takes the current time as a parameter; the shell owns exactly one one-second DispatcherTimer that ticks them, renders their `StatusLine()`s (status bar + tray tooltip), and drains their banked minutes. Nothing about either timer is testable only on a machine — the cycle math, the pause freeze, and the once-only completion are pinned in the Core suite.
- **The break reminder is a state, never a dialog (#141).** When a focus block ends, the timer enters `BreakSuggested`: the shell fires ONE tray balloon (through the ordinary quiet-hours/Do-Not-Disturb gate) and leaves the offer in the status line. Taking the break is a menu click; ignoring it costs nothing. A modal "take a break" prompt was rejected outright — a focus feature that interrupts focus is self-defeating.
- **Focus time counts only time actually spent (#141/#142/#150).** Completed blocks bank their full length; a stop banks whole elapsed minutes; paused session time moves the phase end, so it never counts as work. The stats are honest about being app-side counts: they measure the timers, not the user's attention.
- **Focus mode fills the screen (#141).** Entering focus mode now also maximizes the main window (the prior window state is restored on exit; F11 full screen still manages itself). The pre-R5 focus mode only hid chrome; the item asked for "one window fills the screen", and a windowed rectangle with hidden bars is not that.
- **The session timer crosses at most one phase boundary per tick (#142).** A machine asleep through three phases wakes into the NEXT phase at full length instead of fast-forwarding through cycles nobody lived (and banking their minutes). The banked time stays truthful, and the balloon count stays at one.
- **The reading list stores routes, extending the R2 discipline (#143).** Entries are built by `AppRoute.FromUrl`, which refuses every non-muse.ai URL — so the list can only hold Muse pages, and an entry can never contain a query string or a token. Accepted cost (in KNOWN_LIMITATIONS): no saving arbitrary web pages; that is a bookmark manager's job, and this app deliberately has no general browsing-history store to build one on.
- **Groups-lite are session-only because window ids are (#144).** A group names live window ids; persisting it would resurrect references to windows that no longer exist — which is exactly what R2 workspaces (saved layouts, re-applied through the planner) already solve properly. Groups therefore live ungrouped-or-grouped in memory, prune themselves against the live window list every time the switcher opens, and are gone at exit. The two features are documented as distinct wherever both appear.
- **History search covers the session, and says so (#145).** The app keeps no cross-session browsing history — a privacy property, not a gap — so the searchable corpus is the windows' session `NavigationHistory` plus window titles. Duplicates collapse to the most recent visit; result rows show title + PATH only. The palette payload is the URL itself, in-process only, under the downloads-provider precedent (a file path rides the same way); navigation back to it passes the ordinary link policy.
- **The digest is generated, never scheduled (#146).** #147 exists and could trivially fire the digest daily — but a summary that appears unasked is a notification in disguise. The digest builds fresh from the local stores on the one action that asks for it; the scheduler can run that action only if the user explicitly schedules it.
- **Schedules can name only built-in actions (#147).** A rule's command id must be in `CommandRegistry.BuiltinActions` — sanitization drops anything else, so a hand-edited settings file cannot make the scheduler open a profile, a window, or a file path at 9 AM. Due rules are stamped BEFORE they run and the settings saved first: a failing command cannot refire every tick. And the app registers nothing with Windows Task Scheduler — schedules live and die with the process, which the Settings section, the rule dialog, and KNOWN_LIMITATIONS all state.
- **The quick-note hotkey is a second registration, not a second system (#148).** The S11 manager generalized (registration id + resolver + wording as parameters); Core's `QuickNoteHotkey` mirrors `GlobalHotkey.Resolve` and adds one rule: never equal to the show/hide gesture. It is OFF by default. A global key you didn't ask for is a landmine; the menu and palette capture works without it. The in-app shortcut editor gained the mirror check (an in-app key may not take the note hotkey's combination while it's on), extending the S11 composition rule.
- **Weekly stats extend the #129 file discipline (#150).** Per-profile per-week counts (Monday 00:00 UTC) in `weekly-stats.json`: launches recorded beside the #129 tally at startup, downloads at completion, focus minutes drained from the timers. Bars scale to the week's best per metric — computed in Core, so the dashboard window does no math. Clearing deletes the one file; the digest reads the same tallies (plus the download history's own completion stamps, the real record for downloads).

## 2026-10-25 — v1.4.0 Round 2 Slice R4: downloads round 2 (items 131–140)

- **Sorting is plan → preview → apply → journal (#131/#138).** The Core planner never touches the disk: it emits moves (custom rules first, then the category rules; the archive hook beats both for old files), the shell shows the plan, applies only the approved moves, and journals each batch so Undo can reverse it. Neither a plan nor an undo ever overwrites — collisions rename through the existing UniqueFileName, checked against the disk AND the moves already planned. A rule's target subfolder is sanitized to a plain relative subfolder (never rooted, never drive-qualified, never containing "..") with the Windows shapes rejected explicitly on any host OS, because the shell moves real files by it. Auto-sort on completion is opt-in (default off); the manual Sort with preview is always available. This extends the S2 collision/unique-name discipline rather than adding a second mover.
- **The bandwidth limit is a governor, not a throttle (#132).** The pinned WebView2 SDK (1.0.4258.31) exposes no per-transfer rate control, so the limit pauses the NEWEST transfer while the measured aggregate speed is over it and resumes governor-paused transfers once the total is under an 85% hysteresis band, one step per pump tick so borderline speeds don't flap. A user's own pauses are never touched: the governor tracks exactly the ids it paused and only ever resumes those.
- **Quiet hours defer only KNOWN-large files (#132).** A download's size exists only when the server reports one; holding every unknown-size download would stall more than it saves, so unknown sizes pass. Threshold 0 means "hold everything", which is then the user's explicit choice. Held downloads keep their URIs in memory only — the S2 #15 session discipline — are re-checked against the current schedule when their window ends, and are forgotten at exit rather than written to disk.
- **Duplicate detection is name+size; hashing stays on demand (#133/#136).** Hashing every finished file whenever a new download starts is real disk work for a rare event, so the guard compares file name and size (history entry + the file still being on disk) and asks; "keep both" reuses the collision unique-name machinery. The SHA-256 comparison lives behind the explicit Verify action, whose verdict persists on the history entry so the state outlives the window. The guard is skipped in the Ask-where-to-save flow, where the user is already choosing the destination consciously.
- **Batch capture introduces the in-flight cap (#134).** No global concurrency cap existed before R4; `DownloadConcurrency.MaxConcurrentDownloads` = 4 now governs batch starts (page downloads and retries are user-paced already, so the cap binds the one source that can ask for a hundred transfers at once). Batch links are validated in Core (http/https + host, deduped, capped at 100), confirmed as a list in the window, and started through the same hidden-view engine as retries — URIs in memory, host+path in the log, never a full URL anywhere.
- **Auto-retry is an allowlist, bounded, and announced (#139).** Only network/server interrupt reasons retry — disk, permission, and user reasons would fail identically and spam — at most 1–5 attempts on a deterministic 10/30/90/270 s (5-minute-capped) backoff, each wait announced in the status bar and logged with the file name only. Attempts key on the target path and clear on success; the retry rides the session-failed record, so a manual retry first makes the automatic one stand down. The reason reaches Core as the WebView2 enum's NAME, keeping Core free of the SDK.
- **Quotas warn, never enforce (#140).** The per-profile cap is a soft budget over the profile's downloads folder, measured with the existing defensive folder walk (ProfileDataInfo), with heads-ups at 80% and 100%. Blocking or deleting on a quota would make a bookkeeping feature destructive — out of scope by design. The quota is a profile SETTING (like the S8 data cap), so it copies on clone and travels in profile bundles; usage numbers never travel anywhere.

## 2026-10-25 — v1.3.0 Round 2 Slice R3: profiles round 2 (items 121–130)

- **Avatar glyphs reuse the workspace glyph palette (#121).** One fixed text palette for profile and workspace marks alike: identical rendering on every switcher surface, a stored KEY that sanitization can police, no icon fonts or image assets. The drawn shortcut icon is the one place pixels are generated — drawn fresh from Core's `ProfileAvatar.IconSpec` (color hex + glyph-or-initial) on every shortcut creation, so "regenerating the icon" is simply re-creating the shortcut. A text label gets ONE leading mark: the glyph when set, else the S3 color dot (`Profiles.DisplayLabel`; `MenuLabel` itself is unchanged and remains pinned by the S3 tests).
- **A profile PIN is the app lock's record, per profile (#122).** The same salted PBKDF2 record, cost, constant-time verification, and fail-open repair — stored on the profile instead of the settings root, enforced by `ProfileLock` over the AppLock primitives. The global lock still gates first at startup; a hidden (tray) launch defers the profile gate to the first real show, per the S7/S11 hidden-start contract. The record NEVER travels: clone, copy-settings, and profile bundles all exclude it by construction — the bundle builds its carried copy field-by-field so a field added to AccountProfile later cannot start leaking into exports by accident.
- **The schedule is a suggestion engine with a manual hold (#123).** Rules evaluate against a caller-supplied local "now" (the AppLockThrottle pattern), so the whole engine is deterministic and unit-tested in Core; the shell passes `DateTimeOffset.Now` from a one-minute timer. Ask-first is the default and auto-switch is the opt-in. Choosing a profile by hand — or declining a suggestion — records a hold until the running window ends (or the next one begins), so one manual choice silences the schedule for that window, not forever. Rules name the day the window STARTS, so a 22:00–06:00 window masked for Friday covers Friday night into Saturday. Archiving a profile sanitizes its rule away (archiving pauses its schedule), and nothing is evaluated while the app isn't running.
- **Archive is a visibility flag, not a data state (#130).** Every switcher surface — ⋯ menu, tray, palette, chords, the indicator's count — reads the same Core filter (`Profiles.Visible`), and nothing is ever deleted or moved. An EXPLICIT launch (a desktop shortcut or a musedesktop:// link naming the profile) still opens an archived profile: naming one on purpose is not a switcher. The active profile cannot be archived (Settings disables the box; Sanitized un-archives it as a fail-safe), so the app can never be running a profile its own surfaces pretend doesn't exist.
- **Groups are organization only (#127).** A group is a name plus membership — deleting one ungroups its profiles and changes nothing else. "Switch to group" resolves at RUN time to the most recently used visible member (`ProfileGroups.SwitchTarget`), so the palette can name the destination honestly in the command's detail and the target is still fresh when the command runs, not when the palette was built.
- **Health is counts-only by construction (#125).** Core's report builder receives only numbers: folder bytes from the existing walk, disposable-cache bytes summed from the existing cleanup plan's candidates, a cookie COUNT from the privacy gateway's summary (its domain list is never read on this path), and the newest settings-backup stamp from the rotation catalog. There is no code path that could hand it a cookie name, a domain, a file path, or a page datum — that is the privacy property, enforced by the shape of the facts record rather than by care at call sites.
- **Bundles self-describe and can't be mistaken for settings (#126).** The plain form opens with a `MUSEDESKTOP-PROFILE` magic line, so the settings importer rejects a bundle outright instead of importing near-default settings from its JSON. The encrypted form reuses the S7 envelope around that same text with the bundle kind inside the payload, so an encrypted bundle fed to Settings import decrypts and then fails as non-settings content. Import always assigns a fresh id and runs the carried fields through `Profiles.EnsureValid` — never an overwrite, never a merge, and hand-edited bundle fields get the same repairs as a hand-edited settings file.
- **Usage tallies live outside settings (#129).** `profile-usage.json` beside settings.json, stamped by App at startup beside the LastUsedUtc stamp, best-effort (a failed tally never blocks a launch, and Reset-all-settings doesn't clear it — it isn't a preference). Outside settings on purpose: the counts ride no settings export, no profile bundle, and no support bundle; they are this PC's local tallies, shown in Settings and deletable in one click.

## 2026-10-25 — v1.2.0 Round 2 Slice R2: workspaces & sessions (items 111–120)

- **Workspaces store app ROUTES, never page URLs (#111/#114/#117/#118).** Every surface that remembers a window — a saved workspace, the one-off snapshot, the crash/auto-save journal — stores `AppRoute`: the muse.ai path only, with query and fragment stripped by construction (`AppRoute.FromUrl` refuses any URL whose host isn't exactly `muse.ai`). The redaction argument is the codebase's standing one (never log/store a full URL) taken one step further: a query string can carry a conversation id or a token, and there is no honest reason for a layout file to hold one. The accepted cost, stated in KNOWN_LIMITATIONS: restoring lands on the section, not the exact scroll/conversation state.
- **One profile per process shapes Apply (#112).** Profiles own the WebView2 environment for the process lifetime (v0.3.0), and every window in the app shares the active profile — so a real workspace always names exactly one profile, and applying another profile's workspace restarts the app into it: with the user's OK, the workspace id is parked in `PendingWorkspaceApplyId` and the normal profile switch runs; the new process applies it at startup. A hand-edited workspace naming several profiles applies only its own profile's windows and logs how many were skipped. The alternatives — half-applying silently, or tearing down the environment in-process — were both rejected (the first lies, the second fights the SDK).
- **The apply planner is pure; the shell only executes (#112).** `WorkspaceApplyPlanner` computes the whole diff from (target, current windows, active profile, downloads in flight): main-window route change, windows to open, windows to close, kept windows, and the `RequiresDownloadConfirmation` flag. Matching is multiset-based (two identical secondary windows are interchangeable), the main window is matched first and NEVER closed (it navigates instead), and an empty target closes secondaries only. The download ask is a plan output, not shell logic, because both halves of it are Core-testable facts: closing a window does not cancel its download (the tracker owns downloads since S2) — the ask exists so the user isn't surprised their window closed mid-download.
- **Snapshot and journal are two files on purpose (#114 vs #117/#118).** `session-snapshot.json` is the user's deliberate one-off record; `session-journal.json` is the app's own bookkeeping (open windows + CleanExit + BecameHealthy + WasRestored). Sharing one file would let constant journal writes clobber the user's snapshot, or the snapshot freeze the journal. Both sit beside settings.json, both are routes-only, both load leniently (missing/corrupt = none).
- **Crash restore offers once and cannot loop (#117).** The journal's `CleanExit` flag is the whole crash detector — written false while running, true only on the clean-exit path (the profile-switch restart writes it true too, so a restart is never misread as a crash). After an unclean exit the offer is made once per launch; if the journal says the previous session WAS a restore and no page loaded successfully before it died (`WasRestored && !BecameHealthy`), the offer is suppressed outright — the same no-loop discipline as S8's RecoveryCoordinator, which stays the owner of page/browser-process recovery; this state machine owns window-set recovery only.
- **Startup precedence (#113/#117/#118).** Exactly one arrangement runs at launch, in this order: a pending cross-profile apply (the user already said yes in the previous process), then the journal decision (offer after a crash, silent restore when auto-save is on), then the startup workspace. Safe mode skips all three (a session that might be the problem is never restored in the mode meant to escape it), and a start hidden in the tray defers the arrangement to the first real show — the S7/S11 hidden-start contract, so nothing pops at sign-in.
- **A workspace's accent override is session-only (#115).** Applying a workspace applies its accent through a settings CLONE into ThemeManager; the saved Appearance accent is never rewritten, so removing/switching workspaces returns the user's real accent with zero bookkeeping. Writing `AppSettings.AccentColor` on apply was rejected (apply would become a destructive preference write). Consequence, accepted: the tray icon's profile tint still follows the saved appearance accent, and Settings OK re-applies the override over whatever base the settings just changed.
- **Workspaces ride the settings schema (#116).** No new file format and no migration: the list is a field of `AppSettings` (schema version 2, additive — pre-R2 files load with an empty list, older builds ignore the field), so export/import — plain and password-encrypted — carries workspaces with zero new code paths, and `Sanitized()` repairs them on every load exactly like profiles (dead-profile windows drop, bad routes read as Home, dangling startup/active pointers clear). Reset-all-settings preserves the list as identity/session data while clearing the startup pointer and the auto-save opt-in.
- **Management mirrors profiles' deferred safety (#120).** Rename/glyph/accent/startup edits and delete all happen on the Settings working clone: Cancel discards, OK adopts. Deleting a workspace therefore needs no confirm dialog and no undo system (the dialog IS the undo), never closes a window, and touches no data folder — there is nothing else a layout owns. Apply-from-Settings exists because management without a way to run the thing being managed would send the user hunting through three other menus; it harvests the section's edits first, then follows the profile switch's leave-with-the-clone pattern.
- **Glyphs are a fixed text palette (#119).** Twelve single-glyph choices (★ ● ◆ ■ ▲ ♥ ♪ ☀ ☾ ⚑ ✚ ⌂), the ProfileColors discipline applied to icons: identical on every Windows version, no icon font or image assets to ship, and a stored key (not a character) so sanitization can drop anything unknown. Custom images were rejected for this slice (file management + per-DPI assets for a menu label).

## 2026-10-25 — v1.1.0 Round 2 Slice R1: command palette & window command surface (items 101–110)

- **One fuzzy matcher for the whole shell (#101/#108).** The palette's ranker and Settings search now share Core's `FuzzyMatch`. Two shapes over one scoring core: `Score` (subsequence over a short text — command titles) and `WordScore` (the best single-word score — for keyword blobs, so a Settings term can never borrow letters across words; that's what keeps the S5 pin "profile zoom → Profiles only" true under fuzzy matching). Settings results are RANKED now (title word > keyword word, layout order breaks ties) and the Settings window scrolls to the best match. Source weights in palette ranking keep the surface action-first: an action beats a help page whose title matches the same words.
- **Providers are rebuilt per palette opening (#102).** The registry composes providers over live snapshots (profiles, download history read at open, open-window descriptors); there is no cached command list to go stale, and Core stays free of shell state. The workspaces provider is registered from day one and returns nothing until R2 defines workspaces — an honest seam, not a placeholder feature. Downloads contribute Open + Show-in-folder per completed record (capped at 8); a failed download has no file, so it contributes nothing.
- **Action history stores ACTION IDS ONLY (#106).** The palette's memory is the ids of built-in actions, in a small JSON beside the settings (`palette-history.json`, same atomic write as download history). `Record` refuses any non-action command and the loader refuses any id without the `action.` prefix, so profile ids, file paths, and page titles cannot enter the file even by hand-editing. It is NOT a preference: Reset-all-settings does not clear it, and deleting the file is the (documented) way to clear it.
- **Profile chords are in-app only; no global variant ships (#105).** Ctrl+Shift+1..9 are common browser/IDE chords; registering them system-wide would eat them in every app for the sake of an app that is, by design, usually already focused when you switch its profile. The in-app chords yield to a remapped in-app action that owns the same gesture (they're checked after the remappable dispatch), and Core pins that no chord collides with any catalog default. Chords past the 9th profile simply don't exist (profiles 10–32 use the menus/palette).
- **Ctrl+K and Ctrl+Shift+digits are fixed bindings, outside the remappable catalog.** Same reasoning as S11's global hotkey living outside the S6 catalog: the catalog is the user's remapping surface, and these two are the palette's own front doors. The Shortcuts window doesn't list them yet — the Commands help page (#109) is their documentation home this slice.
- **The commands page is generated, not written (#109).** The Help window appends `CommandsHelp.Render(CommandRegistry.HelpListing())` to the commands page at display time; the registry is the single source for both the palette and the page, and a Core test pins that every listed command appears in the render. The page joins HelpCatalog as its eighth page (S10's count test updated 7 → 8 — the drift guard itself is unchanged: shipped Help.md headings still equal catalog titles exactly).
- **Window actions act on work areas, not monitor rects (#104).** Tiling and next-monitor moves use each monitor's rcWork (added to MonitorRects alongside the existing monitor-rect enumeration), so a tiled window never slides under the taskbar. Focus mode as a window action exists only for the main window (secondaries have no chrome to hide) — modeled on the descriptor (`SupportsFocusMode`), not special-cased in the provider. A secondary window's always-on-top is a session toggle; only the main window's is the persisted setting (through the one `SetAlwaysOnTop` setter the pin, menu, and palette now share).

## 2026-10-24 — v1.0.0 Slice 11: Windows & Muse workflow integration (items 96–100)

- **The global hotkey lives OUTSIDE the S6 shortcut catalog, deliberately (#96).** S6 pinned the catalog as exactly the in-app actions (three remappable, no Global scope) — a Windows-wide RegisterHotKey binding is a different kind of thing (registered with the OS, fires while other apps have focus, can fail because another app owns the combination), so it gets its own settings fields (`GlobalHotkeyEnabled`, `GlobalHotkeyGesture`) and its own Core planner (`GlobalHotkey`). The two systems compose through conflict checks in BOTH directions: the planner refuses an in-app gesture as the global one, and the Settings capture refuses the global combination as an in-app one. The gesture still uses the shared `ShortcutGesture` text format and the same capture UI pattern.
- **The hotkey message hook lives on the main window's handle (#96).** The obvious candidates don't work: the single-instance wake "channel" is an `EventWaitHandle` (a named kernel event — it has no window and cannot host a hotkey), and the tray icon is WinForms-owned by TrayController. The main window's HWND does work: the window is hidden to the tray, never destroyed, for the whole process lifetime, so an `HwndSource` hook attached at `OnSourceInitialized` survives every hide/show cycle. Registration uses MOD_NOREPEAT, is re-applied after every Settings OK (the old combination is freed first), and is released on exit. A failed registration is a status line in Settings + a log line with the Win32 error — never a crash, never a silently dead key.
- **One intent model for every outside ask (#99/#100).** CLI flags, `musedesktop://` links, Jump List tasks, and per-profile shortcuts all resolve to Core's `LaunchIntent` before anything touches the UI. Second launches hand the intent to the running instance through a small file (`pending-intent.json` in the settings folder, written atomically BEFORE the existing wake event is set — the file is the message, the event is the knock; a named pipe was the alternative and lost on moving parts). The pending file holds no URLs — only an intent kind and, for a profile switch, a profile id.
- **While locked, NOTHING applies (#99).** Every intent — including a profile switch, where "show the lock only" was the alternative — queues behind the lock (single slot, last one wins, so an unlock never replays a backlog) and the lock screen is the only response. After unlock, the queued intent applies through the same path as a live one; a queued profile switch still asks before switching. Cold-start links ride the normal startup and apply after first load, through the same gate.
- **The protocol is an allowlist with no parameters, by construction (#99).** Routes are exactly open/home/settings/downloads/help/profile/<id>. Any query string, fragment, userinfo, or port is a refusal (logged scheme+host+path only, ≤120 chars): a `?url=` parameter would turn every link into a remote control for the browser, which is precisely what the app exists to refuse. A well-formed profile route with an unknown id degrades to "show the window + log", never a crash. Registration policy mirrors that conservatism: the installer writes the per-user key; the app syncs it to the Settings toggle (that sync is how portable installs register); a registration owned by ANOTHER app is reported in Settings and never overwritten or removed; uninstall removes the key only when its command still points at that install.
- **Quick dictate ends at the page's door, honestly (#97).** The chain is: show window → `WebView2.Focus()` so keyboard focus is inside the Muse page → status line states the next step. There is no script injection into muse.ai (a standing program rule — no ExecuteScript into the page, no DOM access), so MuseDesktop cannot press Muse's voice button or move the page's own focus; if Muse's UI takes focus from there, that's Muse's behavior, not a promise. The mic check reads S7's machinery: granted this session, or Muse's saved Allow record, means "ready"; otherwise the status line says the microphone still needs granting via Muse's voice button — the feature never fakes a dictation start. No second global key was added: dictate rides the tray item, the Jump List, and `--dictate`.
- **Drag & drop needed guidance, not plumbing (#98).** Verified against the pinned SDK (1.0.4258.31): the windowed WebView2 controller exposes NO drag/drop events or settings (its only drag member is on the composition controller, which this app doesn't use) — WebView2 registers its own OLE drop target on its child window, so file drops onto the Muse page already worked end-to-end and the shell never blocked them. The shell adds only what WPF can actually see: drags over the app's own chrome light the frame ring (the S6 focus ring, shared state) and set a status hint; a drop on the chrome explains where files belong. The shell never reads, accepts, or forwards dropped files — there is no code path that could.
- **--help/--version are answered by the launching process (#100).** They show Core's usage text / the version in a dialog and exit BEFORE the single-instance logic — a help ask must never wake the app, queue behind a lock, or wait for a running instance. `--safe-mode` and `--background` are launch-time only: on a running instance they're logged as ignored rather than pretending to re-apply.

## 2026-10-24 — v0.14.0 Slice 10: diagnostics, support & help (items 89–95)

- **The support bundle's settings are sanitized HARDER than a settings export, deliberately (#90).** The Settings window's plain export is the user's private backup: it must restore everything, so it carries the app-lock record (a salted PBKDF2 hash) and per-profile last pages — and S7 added an encrypted variant for exactly that exposure. Fresh installs record the version without showing (no "new" exists for them), the window never precedes the app-lock gate, and a missing section records the version anyway so a packaging slip can't nag every launch.

Compile-checked with makensis against a dummy stage.

## 2026-10-24 — v0.12.0 Slice 8: performance, reliability & recovery (items 71–80)

- **One recovery coordinator owns every automatic reload (#71/#76).** Core's `RecoveryCoordinator` replaced S1's `_autoRetried` flag: renderer exits map to a page reload, browser-process exits to a full web-view recreate, and connectivity signals (network address/availability change, resume from sleep) map to a reload only when the page sits in a failed state. All three share ONE budget — one automatic recovery per incident, refilled only by a successful load — so crash-then-offline-then-wake can never stack into a reload loop. Everything else (GPU/utility process restarts, `RenderProcessUnresponsive`) maps to *None*: WebView2 restarts its helpers itself, and unresponsiveness belongs to the watchdog (#80), which never auto-reloads.
- **Browser-exit recovery recreates the WPF controls, not just the environment (#71).** A WebView2 WPF control is bound to its dead environment; the honest fix is disposing both `WebView2` controls (main + the hidden S2 retry view), constructing fresh ones into the same layout hosts, and re-running the normal init with the last page as the restore URL. The fields are the window's only references, so the rest of the shell is untouched. If recreation itself throws, the failure overlay shows — recovery still ends at a human decision, never a loop.
- **The data cap deletes by allowlist, and the protected set is the point (#75).** `CacheCleanup` can only ever name folders from `DisposableFolderNames` (Cache, Code Cache, GPUCache, GrShaderCache, ShaderCache, DawnCache, GraphiteDawnCache) and explicitly refuses everything in `ProtectedFolderNames` (Network, Local Storage, Session Storage, IndexedDB, WebStorage, Service Worker, Sessions, shared_proto_db, Sync Data) — unknown folders are skipped, not guessed at. Planning is pure Core over measured sizes, oldest-first (least-recently-written first), and tests pin that a plan can never contain a protected name, even at target zero. Cleanup is stamped onto the profile and surfaced in two Settings places; silence was treated as a defect.
- **The watchdog asks, never acts (#80).** A 15 s `ExecuteScriptAsync("1")` ping with a 5 s timeout; two consecutive misses raise a non-modal banner with Reload / Wait (Wait snoozes 2 minutes). It suspends while tray-suspended (a sleeping renderer can't answer — that's not a hang), while locked, after the mic was granted this session (S4's voice heuristic), and while the page plays audio. A script ping can fail during heavy legitimate work — the banner says exactly what was detected and the user decides.
- **Proxy is read, never set (#77).** Audit result: no code anywhere in the app sets WebView2 proxy arguments (`AdditionalBrowserArguments` is never used) — WebView2 follows the per-user WinINET settings, which Diagnostics merely reads (`ProxyEnable`/`ProxyServer`/`AutoConfigURL`). Server strings are sanitized in Core: any `user:pass@` userinfo is stripped before display or logging, so a credential embedded in a proxy string can never leak into the UI or the log.
- **Runtime floor is 120.0, dated and conservative (#78).** `RuntimeHealth.MinimumVersion` = 120.0.0.0 (comment dated 2026-10-24): the first Chromium-120-era Evergreen runtime, old enough that anything below it is genuinely ancient, new enough to matter. The check distinguishes missing / outdated / fixed-version-folder-present / OK; the fixed-version note exists because the app ships Evergreen (`browserExecutableFolder: null`) — a `FixedVersionRuntime*` folder beside the exe silently changes that contract, so it's surfaced rather than honored.
- **Safe mode narrows behavior, never security (#72).** `--safe-mode` (or Shift at launch) skips last-page restore (lands on Home) and the automatic update check; the app lock gate runs exactly as normal — a recovery mode that bypassed the lock would be a lock bypass. Shift detection is best-effort convenience; the flag is the documented contract. The reset wizard reuses S5's backup-first reset and S7's granular clear rather than duplicating them, and blocks its settings step when the backup write fails (the S5 rule).
- **Backups rotate per kind, beside settings (#79).** `auto-{settings|downloads}-{yyyyMMdd-HHmmss}.json` in `RootDir/backups`, keep 5 per kind, at most one automatic backup per kind per day (checked at startup and on settings saves, which are frequent). Names are validated by Core's parser — the S5 reset backups (`settings-backup-*`) live in the same root but are a different family and are never pruned by rotation. Restoring settings goes through `SettingsStore.TryImport` + the window's own copy-in, identical checks to Import.

## 2026-10-24 — v0.11.0 Slice 7: privacy & security (items 61–70)

- **WebView2 APIs were verified against the pinned SDK (1.0.4258.31) before use — one named API does not exist.** Present and used: `CoreWebView2Profile.ClearBrowsingDataAsync(CoreWebView2BrowsingDataKinds)` (Cookies / DiskCache / CacheStorage / AllProfile), `CookieManager.GetCookiesAsync` (null URI = all cookies in the profile), `CoreWebView2Settings.IsPasswordAutosaveEnabled` / `IsGeneralAutofillEnabled`, `CoreWebView2.ServerCertificateErrorDetected` (+ `ClearServerCertificateErrorActionsAsync`), and `CoreWebView2Environment.BrowserVersionString`. **Absent: `CoreWebView2Profile.GetPermissionsAsync`** — the enumeration API the #62 sketch named doesn't exist in the pinned SDK. The fallback is better anyway: `GetNonDefaultPermissionSettingsAsync()` **does** exist and returns exactly the saved (non-default) choices with kind + origin + state, which is what a permissions manager should list; revocation/re-grant goes through `SetPermissionStateAsync` (Allow / Deny / Default = forget). Also present but not needed: a time-range `ClearBrowsingDataAsync(kinds, start, end)` overload — the slice's choices don't include time ranges, so it stays unused rather than growing a UI nobody asked for.
- **Non-active profiles are reached through a throwaway environment, never by file surgery (#61/#63).** Clearing or counting cookies for a profile that isn't running creates a temporary `CoreWebView2Environment` over that profile's data folder plus an invisible controller (against the main window's handle, closed immediately after). The folders are per-profile and no other process holds them, so this is the SDK's own route to the same profile object the live path uses — one code path for kinds/counts, honest per-profile failure reporting, and no hand-deleting of cookie stores behind WebView2's back.
- **#64's design is SEAN's call, taken mid-slice: an in-app password/PIN, not Windows Hello.** The item was originally held for that decision. Consequences: the credential is an app-level secret, stored as a salted PBKDF2-HMAC-SHA256 record (210,000 iterations, 16-byte random salt — the same primitives and cost as #65's encrypted export) in three settings fields (salt, hash, iterations). 4–64 characters, digits or a passphrase; the UI recommends 6+. Setting/changing it from Settings asks for the current credential first when one exists, so a walk-up user at an unattended unlocked session can't swap it.
- **The lock is fail-open by construction, and recovery is a file delete (#64).** An enabled lock whose record is missing/malformed is disabled by `AppSettings.Sanitized()` (and logged via a `[JsonIgnore]` repair flag the shell checks after load) — a damaged or hand-edited settings file can never brick the app. The documented forgotten-password recovery is deleting `settings.json` from the data folder: the lock record lives there, so the lock goes with it; settings return to defaults (including the profile LIST), but the default profile's sign-in survives because cookies live in the separate WebView2 profile folders — the Settings text and KNOWN_LIMITATIONS say exactly this, and a Core test loads a corrupt-record settings file to prove it comes back unlocked.
- **Pre-unlock gating is two-layered (#64).** For a launch that will show a window, App runs a modal `LockWindow` **before MainWindow is constructed** — WebView2 doesn't exist yet, so no page can render or navigate pre-unlock, and closing the gate shuts the app down (no locked zombie). For a hidden tray launch, showing a password modal on autostart would be a surprise, so MainWindow is constructed in locked mode instead: `OnLoaded` defers `InitWebViewAsync` (and the update check) until unlock, and every show path (`ShowFromTray`, tray Settings/Downloads delegates) routes to the lock screen. Mid-session locks gate surfaces, not the engine: the window hides, all other windows (secondary, Downloads, Settings) close, the tray tooltip/menu go plain and content-naming items disable, the download-complete balloon is suppressed — but downloads in flight finish. One `AppLockThrottle` per window session is shared by every lock screen, so closing/reopening one doesn't reset the wrong-try count; the throttle itself (5 fails → 30 s cooldown, success resets, no wipe/lockout-forever) is a Core state machine on caller-supplied time.
- **What the lock does NOT do is stated everywhere it appears (#64).** It stops casual access to the open app. It does not encrypt profile data on disk (the WebView2 folders remain ordinary DPAPI-protected-per-user data), and it is not a sign-out. Settings text, CHANGELOG, and KNOWN_LIMITATIONS all say so in those words.
- **Privacy counters live outside settings (#67).** `privacy-stats.json` next to settings: counts keyed category|kind|host (host-only — `PrivacyStats.CleanHost` rejects anything carrying a path/query into the counter), a capped recent-denials list (20), one since-date, a 200-row cap. Separate file on purpose: counters are this-PC facts and must not ride a settings export to another machine. The hooks are the three existing block sites in MainWindow (blocked navigation, blocked new window, denied permission); the secondary window logs its own blocks but doesn't count them (it's a transient viewer with no stats handle — its blocks still land in the log and in #66's audit).
- **Certificate errors: the app previously had NO handler (#69).** Nothing subscribed to `ServerCertificateErrorDetected`, so WebView2's default applied — its built-in error page (which the app separately disables for navigation errors and replaces with its own overlay) carried certificate failures. Now: a deferral-based modal asks every time, defaulting to Go back; "Continue anyway" sets WebView2's `AlwaysAllow` for that host and is mirrored in an in-memory per-host map — **session-only, never persisted**, so a restart forgets it; the choice is logged (host only). The ⋯ menu's Connection security dialog shows the current host/HTTPS state, certificate subject/issuer/validity on HTTPS, the runtime version, and can forget the session's overrides (`ClearServerCertificateErrorActionsAsync` + clearing the map).
- **Cookie values are never read into UI text (#63).** `GetCookiesAsync` returns values; the gateway's summarizer touches only `Domain` and counts. The site-data rows show totals + distinct-domain counts; the per-domain breakdown exists in the gateway result but the shipped UI doesn't display even names today — counts only. This is a deliberate under-use of the API.
- **The permissions manager is scoped to the running profile, and says so (#62).** The live profile is the only one whose choices can change under a running app; other profiles' choices become visible when that profile runs. The section labels itself "profile MuseDesktop is currently running" rather than implying a global list. Recent denials come from #67's stats (this PC, all profiles — also labeled).
- **Autofill flags are profile-shared in WebView2 (#68).** The SDK documents `IsPasswordAutosaveEnabled`/`IsGeneralAutofillEnabled` as one shared value per profile ("changing one changes the other" across a profile's web views), so applying at the main view's init — and live on Settings OK — genuinely covers secondary windows too. Before this slice the shell hardcoded both to true at init; now they come from settings, defaulting to true = WebView2's own defaults, so no existing user sees a behavior change unless they flip the toggles.
- **Reset-all-settings deliberately does NOT touch the app lock (#64).** `SettingsReset.ApplyDefaults` restores preferences; a credential is not a preference, and a reset silently stripping a security control would be a nasty surprise. Removal lives in the Privacy section, behind an explicit confirm (and, for change, the current credential).
- **The encrypted export envelope is app-detectable and versioned (#65).** Magic first line `MUSEDESKTOP-SETTINGS-ENCRYPTED`, then JSON {version, iterations, salt, nonce, tag, data}: PBKDF2-HMAC-SHA256 (210,000 iterations, 16-byte salt) → AES-256-GCM (12-byte nonce, 16-byte tag), .NET built-ins only. Import distinguishes three failures in plain words — not encrypted / damaged envelope / wrong password or altered data (GCM auth failure) — and the password prompt is never shown for a plain file. The lock hash riding plain exports is disclosed in the export dialog itself when a lock is set.

## 2026-10-24 — v0.10.0 Slice 6: accessibility, keyboard & focus (items 51–60)

- **There is no global hotkey, so #53 remaps only what exists (#52/#53).** Checked the whole shell before designing: no `RegisterHotKey` anywhere; show/hide is the tray icon (click / double-click) plus the single-instance wake event. The item's premise ("remap the global show/hide hotkey") names a feature the app never had, and inventing a new global hotkey was out of scope — so the catalog's `Global` scope exists but is deliberately empty, and the remappable set is the three in-app actions: Settings (Ctrl+, — a real binding since v0.2.0), Downloads and Home, which **had no keyboard gesture at all** before this slice and gained defaults (Ctrl+Shift+D, Alt+Home) precisely so there is something honest to remap. Everything else the shell binds stays in the catalog as fixed. If a global hotkey is ever added, it lands in the catalog as a Global entry and this model already fits it.
- **One catalog, three consumers (#52/#53).** `ShortcutCatalog` in Core is the single source of truth: the Shortcuts window renders it (with effective gestures), the Settings editor edits its remappable subset, and the main window dispatches remappable actions by comparing the pressed gesture against `ShortcutBindings.EffectiveGesture`. Overrides live in settings as action-id → canonical gesture text ("Ctrl+Shift+D"). Sanitizing uses final-state semantics (catalog order, first claim wins; an override may take another action's default only when that action has itself moved) so a settings file can never encode an ambiguity the dispatcher would have to guess at; equality with a fixed gesture is a conflict even in storage. Overrides require Ctrl or Alt — a bare key would fire while typing. The main window checks remappable gestures BEFORE the fixed Ctrl block, which is safe precisely because sanitize/TrySet guarantee an override can never equal a fixed gesture.

Neither collides with any existing binding or with Chromium conventions the page relies on; both are in the gesture-eligible key set (Core whitelists letters/digits/F-keys/nav/OEM keys — Escape is deliberately NOT gesture-eligible, since Esc is the universal cancel and the find/fullscreen handler owns it).
- **Reduce motion gates the flash, and that's the whole surface (#55).** The shell has NO storyboard/transition animations — verified by reading the shell: every state change is an instant Visibility/brush swap (focus mode, menus, overlays). The one motion-like effect the shell produces is the S4 taskbar attention flash (`FlashWindowEx` is an OS effect), so `MotionPolicy` gates exactly that, with a log line when it suppresses. The Windows side reads SPI_GETCLIENTAREAANIMATION via SystemParametersInfo (the documented query behind the Settings "Animation effects" toggle). Page motion is Chromium's business: the web view already honors Windows' setting through prefers-reduced-motion, and the app does not inject anything into the page. Claiming more surface than this would be inventing it.
- **High Contrast = SystemColors, applied as overrides after the palette (#51).** When `SystemParameters.HighContrast` is on, ThemeManager repaints every shell token from the system role that matches it (Window/WindowText for surfaces and text, Control for raised, GrayText for faint, Highlight/HighlightText for the accent/fill/text-on-accent triple). This runs inside the same in-place brush mutation S5 established, so open windows repaint; and App now re-applies the theme on EVERY UserPreferenceChanged (S5 re-applied only in Follow-Windows mode) so an HC toggle lands live. Four hard-coded `Foreground="White"` accent buttons (reload overlay, Settings OK, Downloads Open, wizard Save) moved to the new `AccentTextBrush` token so HC can pair Highlight with HighlightText. What code inspection can verify: the palette mapping exists, is complete over the token set, and the title-bar/DWM path is unchanged. What it cannot: that every pixel is legible in all four Windows HC themes — that is the on-machine pass in RELEASE_CHECKLIST.
- **Focus visuals: one explicit style, applied implicitly + inside local styles (#51).** App.xaml defines `ShellFocusVisual` (a 2px accent border template) and implicit FocusVisualStyle setters for the interactive control types. WPF's default focus visual is theme-dependent and effectively invisible on this dark shell; worse, SettingsWindow's window-local CheckBox/RadioButton styles silently dropped any inherited focus visual, so they now set it explicitly too. Focus order needed no surgery: every window's XAML declaration order IS the logical tab order (verified by reading each window top to bottom during the pass).
- **The #59 audit is a test, scoped to XAML-declared controls.** `XamlAccessibilityAuditTests` parses every `src/MuseDesktop/*.xaml`, walks elements skipping DataTemplate/ItemTemplate subtrees (their content is data, not controls), and fails any Button/MenuItem/TextBox/ComboBox/CheckBox/RadioButton/Hyperlink/ToggleButton/ListBox with no AutomationProperties.Name, ToolTip, Content, Header, or inner text. The repo root is located by walking up from the test ASSEMBLY's location (AppContext.BaseDirectory points at the console runner under our gate — a real bug caught while writing it). Controls created in code (Settings' shortcut rows, toolbar editor checkboxes) are outside its reach by construction — they set Content/ToolTip in code, and the audit's scope note says so. On its first run it flagged exactly four controls — Downloads' two ListBoxes and Settings' two zoom ComboBoxes — all fixed in this slice.
- **Placement clamping is per-monitor-rect math in Core (#60).** The old restore check used one virtual-screen bounding box, which passes a window stranded on a disconnected monitor whenever the box still covers the point, and knows nothing of per-monitor scale. Now: the shell enumerates monitors (EnumDisplayMonitors + GetMonitorInfo), converts each PHYSICAL rect to DIPs at that monitor's own GetDpiForMonitor scale, and Core's `PlacementClamp` keeps the window if ≥80×40 DIPs of it show on any single monitor (the old minimum-visible rule), else fits it into the primary. Any enumeration failure falls back to the old virtual-screen single-"monitor" behavior. The manifest's PerMonitorV2 declaration was previously only a comment claiming the .NET default; it is now explicit (`<dpiAware>` + `<dpiAwareness>`), and the WinForms analyzer's WFO0003 objection is suppressed in the shell project with a comment — WPF reads DPI awareness from the manifest, not from the WinForms-only SetHighDpiMode API.
- **Zoom steps: finer near 100%, extremes behind a setting (#57).** The standard table now steps 5% between 75% and 125% (25-point jumps at the ends), because eyes notice a 10% jump at reading size and don't at 50%. The extended table inserts 25%/33% below and 250–500% above, and exists only when the setting is on — clamping, per-profile zoom sanitizing, and Settings' combo lists all take the same flag, so a 300% zoom can never be stored while the range is off (it clamps to 200% at load instead of stranding the page somewhere the UI can't represent). Two pre-S6 Core test expectations changed with the table (step from 100% is now 105%, not 110%) — the table IS the behavior the item asked for.

- **Accents have two variants each (#44) — one hex cannot do this job.** A single accent would need ≥ 4.5:1 as text on a near-black background AND on a near-white one AND under white button text; the luminance bounds contradict each other (the family red #E50914 measures 4.10:1 on the dark background — it was always decoration-grade there, never text-grade). So `AccentPalette` stores a brighter dark-shell variant (text/decoration on dark) and a deeper light-shell variant (text on light, and the FILL for accent buttons in both themes, where white-on-fill is ≥ 4.5:1 — pinned per accent by tests). Call sites that fill a button with white text use the new `AccentFillBrush`; text call sites keep `AccentBrush`. Profile colors (#24) are a separate palette and are not conflated with this one.
- **Toolbar layout is (order, hidden), not a single visible-list (#45).** Settings store every known button id in display order plus a hidden set. That split is what lets sanitize append a future new button at its canonical position instead of mistaking "absent" for "user hid it". Back can never be hidden (the toolbar must always offer navigation) and the ⋯ menu is not a layout item at all — fixed, last, always available, since it is the only route to Settings/Downloads. The shell does not rebuild buttons: the XAML declares them once with handlers/styles, and `ApplyToolbarLayout` only re-parents them into the strips in the saved order, omitting hidden ones. Reorder in Settings moves within the combined list; the left/right grouping is a property of each button, not something the user can break.
- **Shell text size scales locally-set font sizes from remembered design values (#46).** `ShellTextScaling` walks a window's logical tree, multiplies each locally-set FontSize by the factor (100/125/150, Core-snapped), and remembers the design size per element so re-applying never compounds; the window's inherited base size scales too. Reached: main window, Settings, Downloads, the wizard, and the ⋯ menu (applied explicitly on open — pop-ups live outside the window tree). NOT reached, stated in KNOWN_LIMITATIONS: the WinForms tray menu (Windows draws its font) and the second window (it has no shell text of its own beyond the title bar). No Viewbox scaling — text stays text.
- **The start-page choice is a 3-way mode on the profile (#47), migrating the v0.4.0 bool.** `AccountProfile.StartPage` (LastPage / Home / Custom) extends `StartAtHome`; `EnsureValid` migrates a pre-v0.9.0 file's bool into the mode on first load and keeps the bool rewritten from the mode thereafter, so a downgrade still reads the choice correctly. Validation is launch-time (`StartPagePolicy`): a custom URL must be an absolute HTTPS URL on an in-app host passing the ordinary navigation policy; invalid → Home + a log line with the value redacted. The stored string is only trimmed and length-capped — validation at use, not at save, so a typo is fixable in place and the fallback behavior is one tested code path.
- **Reset-all is preference-only, and the backup is a precondition (#42).** `SettingsReset.ApplyDefaults` copies defaults into every preference field while preserving identity/session state: profiles, the active id, per-profile last pages, window placements, the deferred-deletion queue, and the Settings-window memory. Resetting must never sign anyone out of an account or orphan a profile folder — profile removal is its own explicit, data-deleting action. FirstRunCompleted IS reset (a reset returns the app to first-run state, wizard included). In the shell the flow is: confirm → export the pre-reset settings to `settings-backup-<timestamp>.json` in the settings folder → only then apply. If the backup write fails, the reset does not happen; the note in the window says so. Import undoes a reset completely.
- **Portable mode is a marker file, not a setting (#49).** A settings-held "portable" flag would be circular (the settings file's location is what it decides). `portable.txt` beside the exe → settings/download-history/logs root becomes `<exe dir>\data`, resolved in Core (`SettingsLocation`) and consumed through the existing `AppPaths` properties, so no caller changed. Nothing migrates automatically in either direction: entering portable mode starts fresh, removing the marker returns to the installed data untouched — silent data movement is exactly what a portable user carrying a USB stick does not want to discover later. Scope limit, stated plainly: the **WebView2 sign-in profiles stay in %LOCALAPPDATA%** in this version — #49 as specified covers settings + download history; moving the (large, lock-sensitive) browser profile is a separate decision for a later slice.
- **The first-run wizard edits a clone and never persists itself (#50).** One window, the four highest-regret defaults (close-to-tray, start-with-Windows, downloads folder, update checks), pre-filled with current values. App shows it once — when `FirstRunCompleted` is false — and ANY exit (Save, Skip, the X) records completion: a wizard that nags twice has failed its only job. A first run also never starts hidden (the wizard needs a visible owner). One subtlety: pre-v0.9.0 settings files have no such flag, so an upgrader's file would read as "first run" — App distinguishes by the settings schema marker (pre-v0.9.0 files load as schema < 2): an existing file from an older build is an upgrade, not a first run, and is silently marked completed; `SettingsReset` deliberately preserves SchemaVersion so a post-reset launch (schema 2, flag false) still re-offers the wizard as designed. Re-running from Settings edits the Settings window's working clone and refreshes its controls, so a wizard change can't fight the clone/OK flow. Two name collisions worth noting for future slices: .NET 10 WPF has its own experimental `System.Windows.ThemeMode`, so shell code fully qualifies `MuseDesktop.Core.ThemeMode`; and WinForms global usings force fully-qualified media types in the new shell files, as elsewhere.

## 2026-10-24 — v0.8.0 Slice 4: tray, notifications & presence (items 31–40)

- **Attention signal (#31): the document title's leading "(N)" prefix, and nothing else.** Muse's page offers the app no unread API. The one defensible signal is the widespread title convention ("(3) Muse" = 3 unread) that Gmail/Slack/Discord use. The Core parser (`AttentionSignal.Parse`) accepts exactly that shape — leading parentheses, digits only, ≤4 digits, followed by whitespace or end-of-title — and returns None for everything else, including "(0)", "(Official) Muse", and counts elsewhere in the title. Muse's favicon badge was rejected as a signal: WebView2's `FaviconChanged` hands over an image, and pixel-guessing a badge out of it is exactly the kind of inference this feature forbids. Consequence, accepted knowingly: if muse.ai does not use the "(N)" convention, the badge never appears. That is the correct failure mode for a "never guess" feature. The taskbar mirror uses WPF `TaskbarItemInfo.Overlay`; the tray badge is painted onto the icon (top-right; profile dot bottom-left — the split layout is a Core plan, `TrayIconPlanner`, the pixels are the shell's `TrayIconRenderer`).

The backstop that does exist: `TrySuspendAsync` itself is WebView2's call and the page can decline it; the app already logs that outcome. Adding `IsDocumentPlayingAudio` as a second input was rejected — a chat reply being read aloud is output, and suspending mid-playback is WebView2's decline case, not something to double-guess.

The pinned SDK does expose `CoreWebView2.NotificationReceived` — intercepting it could gate muse.ai's own toasts, but setting Handled there makes this app responsible for re-delivering another app's notifications (or silently eating them), which changes behavior we don't own; deliberate non-interception, revisit only with a full toast implementation. Standing limit inherited from #23, stated on the items themselves: while the app is running, single-instance wakes the window and the task's argument is not forwarded — profile Jump Tasks switch only a not-yet-running app.

No tray-specific duplicates to drift. The suspend status line is informational (`TrayStatusText` in Core) and refreshed on menu open, as are the downloads and profile submenus.

## 2026-10-24 — v0.7.0 Slice 3: profiles & accounts (items 23–30)

- **Shortcut mechanism (#23): WScript.Shell late-bound COM, and --profile persists like a switch.** The .lnk is written through `Type.GetTypeFromProgID("WScript.Shell")` + `Activator` (the dynamic COM pattern TaskbarProgress already uses), not IShellLink P/Invoke — a dozen lines, no vtable declarations to get wrong, failure-tolerant with a plain error in Settings. Arguments are parsed by a new Core `CommandLine` parser (the start of item 100's CLI surface: --background, --smoke-test, --profile in both `--profile x` and `--profile=x` forms; unknown args collected, never fatal). Invalid/unknown ids fall back to the saved active profile with a log line. Stated limit: while the app is already running, single-instance still just wakes the running window — a shortcut does not switch a running instance.

While an override exists, zoom gestures (Ctrl +/−/0, toolbar, page zoom control) persist to the override (via `PersistZoom` at save points) and the shared zoom is not touched; the Settings shared-zoom field likewise applies only to profiles without an override. Turning the override off returns the profile to the shared zoom at its current value. This keeps "my Work profile is at 125%" from drifting the shared default every other profile uses.
- **Deferred folder deletion (#28): a persisted id queue, retried pre-environment.** Settings stores `PendingProfileFolderDeletions`. Removal still deletes immediately when it can; the running profile's folder and failed deletes are queued instead (previously: the folder stayed forever, per the old KNOWN_LIMITATIONS). At startup — after the single-instance check, before the main window exists, hence before any WebView2 environment can hold a folder open — each queued folder delete is retried, never for the profile being launched. Sanitization is the safety net: the list is deduped, valid ids only, capped, and **any id naming a live profile is dropped**, so a re-created profile can never have its folder deleted out from under it.
- **Profile cap (#30): 32 hard, 8 soft.** `Profiles.MaxProfiles` 8 → 32 (EnsureValid truncates deterministically from the tail, as before). The old 8 becomes `SoftProfileWarningThreshold`: the Settings Add flow confirms past it, because the real cost of many profiles is disk (a full WebView2 data folder each), not correctness.
- **Copy-settings is a Core whitelist (#29).** `Profiles.CopySettingsFrom` copies exactly StartAtHome, DownloadsFolder, ZoomFactor, DisplayColor into a fresh id/name. Everything session-adjacent is excluded by construction: LastUsedUtc starts null, and last pages live in `LastUrlByProfile` under the profile's own id, so a new id has none. Tests pin both directions.
- **Colors are a fixed palette of keys (#24),** stored as names ("Blue"), painted from Core hex values. Unknown keys sanitize to none, so settings files can't invent colors and the palette can evolve without breaking old files. ## 2026-10-24 — v0.6.0 Slice 2: downloads (items 13–22)

- **Pause/resume API finding (#14): PRESENT in the pinned SDK, no fallback or fake needed.** The 1.0.4258.31 package's Core XML documents `CoreWebView2DownloadOperation.Pause()`, `.Resume()`, and `.CanResume`, plus the `UserPaused` interrupt reason. Semantics that shaped the tracker: pausing moves the operation to `Interrupted` with reason `UserPaused` — so "interrupted" is not synonymous with "failed". The tracker treats `UserPaused` as a first-class Paused state (stays tracked, no history record, Resume offered per `CanResume`), `UserCanceled` as cancelled (no record), and every other interrupt reason as a failure. (The SDK's own Pause summary text says "UserCanceled" — that contradicts its `UserPaused` enum member and the documented resume flow; the enum is what the code keys on, and the S2 on-machine pass must confirm the reason value in practice.)
- **Retry mechanism (#15): a hidden WebView2 on the same environment, in-session only — and why nothing stronger exists.** Download source URLs are never persisted (standing rule), so after a failure the URI survives only in the shell's memory (`SessionFailedDownload`). Retry creates a 1×1 hidden WebView2 from the main window's existing `CoreWebView2Environment` (same profile/sign-in), wires its `DownloadStarting` to the *same* handler the main view uses — so destination policy (effective folder, ask-where-to-save, collision handling) is identical — and navigates it to the remembered URI. If the server answers with a file, the handler takes the operation over and the tracker follows it like any download. Honest limits: if the server instead returns a page (expired signed link, interstitial), that page loads invisibly in the hidden view and no download starts — a manual re-download from the chat is then the route, and the status bar says the retry was started, never that it succeeded. There is no WebView2 "restart this operation from a URL" API; re-navigation is the only real mechanism, and fabricating a resume of the dead operation was rejected.
- **Failure records in history (#16): a State field, defaulting to Completed.** Old history files have no state field and deserialize as Completed — which is exactly what every pre-v0.6.0 record was. Failed records store the interrupt-reason *name* (e.g. `NetworkFailed`), size-received, and time; never a URL. User-cancelled downloads are deliberately NOT recorded: the user already knows they cancelled, and a history full of cancellations would drown the failures the filter exists to find.
- **The multi-download manager lives in the existing Downloads window (#13),** not a new window or popover: an Active list on top (polled at 750 ms while open, selection preserved by id) over the history list. The status bar keeps the pre-S2 `ProgressStatus` wording byte-for-byte for a single download — the only intentional wording change in the slice is the speed appended to the right-hand detail (#22), implemented as a new overload so the pinned v0.4.0 tests pass unmodified. With several downloads the status bar switches to a Core-computed aggregate; per-file detail lives in the manager.
- **Taskbar progress (#19): ITaskbarList3 via a vtable-prefix interface.** Only the interface prefix through `SetProgressState` is declared (COM slots are positional), the coclass is activated through `Type.GetTypeFromCLSID` + `Activator` (a direct cast from a ComImport coclass doesn't compile), and every call is wrapped so a taskbar failure degrades to a log line. Failure latches the Error state in the main window until the next download starts; a paused-only set shows Paused (yellow).
- **Effective downloads folder (#20) is a Core resolution, not shell branching:** profile override ?? shared folder ?? null, where null deliberately means "leave `ResultFilePath` at WebView2's default" — that's the *system* Downloads folder including when a user has relocated it in Windows, which a hard-coded `%USERPROFILE%\Downloads` would get wrong.
- **Delete-file removes the history entry too (#17).** The alternative (keep a row pointing at a file the user just deleted from inside this window) was rejected as a confusion factory; Clear-history remains the files-untouched route. The confirm dialog states plainly that `File.Delete` is permanent (no Recycle Bin) — if a future slice wants bin semantics it will need a shell API this one deliberately did not fake.

## 2026-10-20 — C# / WPF + WebView2 instead of the usual Rust default

Muse is a website, so the client is a shell around a web view. On Windows the first-party tool for that is Microsoft's WebView2 (Edge/Chromium) with its official .NET SDK: documented APIs for the exact things this app needs — a persistent user-data folder (login session), new-window and navigation events, permission requests, and download operations with progress and ETA.

The Rust alternative (wry/tao) abstracts those away behind a cross-platform API whose surface changes noticeably between minor versions, and exposes downloads/permissions only partially. The concrete advantage — a stable, Microsoft-maintained SDK for the one platform this app targets — outweighs the standing Rust default for this project. Plain logic (URL policy, settings, zoom) lives in a dependency-free `MuseDesktop.Core` library so it stays unit-testable anywhere, and the WPF shell stays thin.

Alternatives considered: Tauri (Rust + WebView2, but a large toolchain/JS build for a single-window shell); Electron (bundles a whole Chromium — hundreds of MB to show one website, and a second browser profile to secure); a PWA shortcut (no tray, no download progress, no link policy — the behaviors that justify a native client at all).

## 2026-10-20 — Framework-dependent publish, Evergreen WebView2

The release is a framework-dependent win-x64 publish (~a few MB) that requires the .NET 8 Desktop Runtime and the Evergreen WebView2 Runtime (preinstalled on Windows 11 / most Windows 10). This keeps downloads small and lets Microsoft service the web engine's security fixes independently of this app. Trade-off: two runtime prerequisites, both detected with a plain-language explanation in-app when missing (WebView2) or by Windows itself (.NET).

## 2026-10-20 — Link and permission policy

- Top-level navigation: any HTTPS page may load (sign-in and connector OAuth flows redirect across providers). HTTP and non-web schemes are refused.
- New-window requests: only Muse and known identity-provider hosts (`muse.ai`, `meta.com`, `facebook.com`, `instagram.com`, `accounts.google.com`, `appleid.apple.com`, `login.microsoftonline.com`, exact host or true subdomain) stay in-app. All other http(s) links open in the user's default browser. Look-alike hosts never match.
- Permissions: auto-grant only `notifications` and `microphone`, only for origin `https://muse.ai`. Everything else is denied and logged. Rationale: notifications are how a long-running agent says "done", and the microphone is Muse's voice input; a desktop client that silently granted camera/geolocation to arbitrary origins would be a liability.

## 2026-10-20 — Downloads handled in the status bar

WebView2's default download flyout is suppressed (`DownloadStarting` → `Handled`) and progress is reported in the app status bar as percent + ETA from the download operation, because that matches how the rest of SEAN's apps report progress and keeps the single-window app self-contained. Files land in the default Downloads folder (WebView2's default path).

## 2026-10-20 — Black/red product-family look

Toolbar and status bar use the family tokens (near-black surfaces `#0B0B0D`/`#141417`, hairline `#2C2C31`, red accent `#E50914`, off-white text), and the Windows title bar is set to immersive dark via `DwmSetWindowAttribute`. The web content itself is Muse's own design and is not restyled — injecting CSS into a third-party app would break with their updates and misrepresent their product.

## 2026-10-20 — Settings format

One JSON file, schema-versioned, written atomically (temp file + replace). A file that fails to parse is copied aside as `settings.json.corrupt-<timestamp>` and defaults are used, so user data is never silently discarded. The WebView2 bootstrapper link used in the missing-runtime message is Microsoft's official fwlink (`https://go.microsoft.com/fwlink/p/?LinkId=2124703`, the Evergreen bootstrapper referenced in Microsoft's WebView2 distribution docs).

## 2026-10-27 — Reliability, download controls, and support-bundle privacy

- **Bulk pause/resume stays on WebView2's own operation contract.** Pause all targets in-progress operations; Resume all targets only paused operations reporting `CanResume`. The UI does not pretend that a server supports range requests or that every paused item can resume.
- **A previewed move batch is transaction-like, not a sequence of independent best efforts.** A later move failure triggers reverse-order rollback. The Core executor is delegate-driven so tests can inject both the primary failure and a rollback failure; files that remain moved are still returned to the existing journal path for recovery.
- **Support bundles omit common local path and profile-label metadata.** The bundle's settings copy drops custom download folders and replaces profile display names; download-history JSON excludes `FullPath`; diagnostics redact path fields and profile names; log excerpts additionally redact common absolute Windows paths. The user still reviews an optional screenshot before inclusion. This is defense in depth, not a guarantee that arbitrary user-authored notes or every possible path spelling is non-identifying.
- **CI retains per-architecture inventory facts.** Each published CI artifact contains a CycloneDX JSON SBOM and `build-info.json` (commit, SDK, RID, configuration). These are inventory/build-input records, not signed attestations; release hashes and signing remain separate.

## 2026-10-27 — Code-block folding is presentation-only

Long code blocks in the hosted conversation receive an expand/collapse control; blocks over 14 lines or 1,000 characters fold after a quiet interval, unless the page exposes an active-generation signal or the user has manually chosen a state. This is a separate, explicitly approved, narrow presentation-only extension to the R5B page-script exception—not a general reopening of page injection. It is a best-effort heuristic, not a change to message content: exports and bookmarks exclude the injected control, and MuseDesktop does not rewrite prompts or set model verbosity. The current integration exposes no Muse-native answer-detail setting; generated-answer detail remains controlled by Muse.

## 2026-10-27 — Async history transaction synchronization

Download history updates now hold a bounded, per-path in-process `SemaphoreSlim` stripe across load, mutation, and atomic save. Sync and async APIs share these transaction gates; the inner `AtomicFile` gate remains separate, and the lock order is always history gate → atomic-file gate. This prevents concurrent note/hash/completion updates from overwriting one another. It does not provide FIFO ordering for conflicting writes or cross-process coordination; the app's single-instance mutex remains the process-level guard. Profile-size invalidation increments a bounded epoch so an older in-flight scan cannot repopulate a cache entry after invalidation.

## 2026-10-27 — Event-driven watchdog and background deadlines

- **Renderer health uses WebView2's native `ProcessFailed` event.** `RenderProcessUnresponsive` directly opens the existing Reload/Wait affordance; the 15-second JavaScript ping, 5-second timeout, and their dispatcher timer are removed. WebView2 repeats the native event while the renderer remains unresponsive. The SDK does not expose a matching recovery callback, so a successful page load clears the banner; choosing Wait dismisses it and snoozes repeated native notifications for two minutes. Nothing auto-reloads.
- **Download queues are event-triggered.** Started/completed/failed/capacity changes service the batch queue. Held quiet-hours downloads share one one-shot dispatcher wakeup at the earliest known end deadline, and resume/time/settings changes recheck them. The bandwidth governor retains a coalesced 5-second one-shot sample only while transfers are active (or a governor-paused transfer is awaiting headroom), because throughput is a time-based signal; it is disarmed when no governor work remains. Tray suspension's former two-minute blocked recheck now waits for download-state or microphone/navigation events instead.
- **Schedule work uses one-shot deadlines.** Profile-window boundaries, hold expiry, and the next command schedule are combined into a single timer. Settings, activation, unlock, download completion, system-time changes, and resume trigger immediate reevaluation and rearming; no minute/15-second background scans remain in normal operation (a failed schedule evaluation gets one delayed retry). The one-second focus/session countdown timer runs only while a countdown is active.
- **Native watchdog recovery limitation:** because WebView2 has no “renderer became responsive” event, an already visible banner is not automatically dismissed solely because a stuck script later resumes; navigation success or the user's Wait/Reload action clears it. This avoids reintroducing script polling.

## 2026-10-27 — Portable local-data backup and staged restore

- **One versioned JSON backup, using the existing .NET cryptography.** The bundle carries settings plus an allowlisted set of local stores: download history, reading lists, notes, weekly stats, bookmarks, drafts, snippets, privacy counters, profile usage, palette recents, and generic activity history. The existing password-encrypted export envelope is offered for the bundle; plain export remains explicit and warned because these records include private text, the app-lock hash, and download paths.
- **Restore is previewed and staged in Settings.** Import validates the format and each store's JSON shape before preview. It applies only after the user presses OK; Cancel changes nothing. The write set is fixed in code (imported names never become paths); each file is written atomically, and a failed batch attempts reverse-order rollback. Download history uses its existing per-path transaction gate. The import is refused while downloads remain active so their later completion cannot overwrite the restored history or counters.
- **Deliberate exclusions:** WebView2 profile folders (cookies/sign-ins), downloaded file contents, logs, update installers, and transient session state. Download history does include the original local paths, which the preview and export warning state plainly.

## 2026-10-27 — Recent activity center privacy boundary

- **Activity rows store only an enum and UTC timestamp.** The display wording is fixed in Core; tray balloon titles, messages, file names, URLs, and conversation text are never persisted. Only notifications actually shown are recorded, the store keeps the newest 100, and the Settings backup includes this small local file.
- **Access stays behind the app lock.** The center opens from the main menu, tray menu, or command palette; clearing history requires confirmation. Persistence uses the existing atomic-file path and no new package or notification framework.

## 2026-10-27 — Tab-host phase 1

The existing WebView2 remains the only visible page. `BrowserHost` provides a replaceable content host, and one `BrowserTabState` owns that view's WebView2 instance, navigation history, readiness, title, and last known good URL. Recovery replaces the view in that host and updates the same state; no tab strip or additional pages are exposed in this phase.

## 2026-10-27 — Tabbed browsing and observable status

- **Tabs keep live pages, not just URLs.** Each of up to 10 tabs owns a WebView2 control, navigation history, title, readiness, and last-good route. Controls share the active profile's WebView2 environment so sign-in remains shared; selecting a tab switches the visible host without discarding page state. Tabs are session-only in this phase, and closing the last tab is refused.
- **Status reports observable work, not inferred model thoughts.** The tab strip shows loading, ready, load-failure, recovery, or renderer-health states; download progress remains in its existing status UI. MuseDesktop cannot change Muse's hosted model verbosity or reveal private internal reasoning, and it does not scrape chat text or inject prompts for this status feature.

## 2026-10-27 — Session restore previews tab routes

The deliberate session snapshot now includes up to 10 sanitized `muse.ai` paths for the main window and the selected-tab index, in addition to its existing window arrangement. Restore displays those paths and secondary-window routes before any changes; Cancel applies nothing. Titles, query strings, sign-in/provider pages, and full URLs are excluded. Older snapshots without tab routes fall back to their saved main-window route. The separate crash journal now records the same safe tab-route set; an offered crash restore previews it, while explicitly enabled auto-save restoration remains silent.
