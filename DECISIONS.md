# Decisions

A living log of significant architecture, UX, security, and dependency decisions.

## 2026-10-24 — v0.14.0 Slice 10: diagnostics, support & help (items 89–95)

- **The support bundle's settings are sanitized HARDER than a settings export, deliberately (#90).** The Settings window's plain export is the user's private backup: it must restore everything, so it carries the app-lock record (a salted PBKDF2 hash) and per-profile last pages — and S7 added an encrypted variant for exactly that exposure. A support bundle exists to be handed to another person, so Core's `SupportBundle.SanitizeSettingsForBundle` strips the lock record ENTIRELY (salt, hash, iterations, and the enabled flag — support learns "app lock: on/off" from diagnostics.txt instead), every last-page URL, and every custom start-page URL. Tests pin the serialized bundle JSON: no lock values, no `http://`/`https://` anywhere. The bundle's log is the redacted tail (S7's `RedactionAudit` applied), never the raw file, and a preview dialog + in-zip manifest state the contents and exclusions before/instead of trust. Nothing is uploaded — the user saves the zip and decides.
- **The microphone test reuses the real permission path, with a narrower grant — not a wider one (#92).** Verified against the pinned SDK (1.0.4258.31): `CoreWebView2.SetVirtualHostNameToFolderMapping` exists, so the test page is served from a temp folder under the reserved host `musedesktop.test` — a secure context, which `getUserMedia` requires (data:/NavigateToString pages have opaque origins and can't request the mic at all). The test window hosts its WebView2 on the ACTIVE profile's environment, so the request travels the real `PermissionRequested` machinery; that window's own handler grants the microphone to the test host only and denies everything else. The production policy (mic/notifications for muse.ai, deny the rest) is untouched and the test host grant dies with the window. The test also measures actual audio (peak level over ~3 s), because a granted-but-muted/wrong-device mic is the common real failure — the saved permission record alone can't prove sound arrives. The S7 permission row for microphone/muse.ai is reported alongside for completeness.
- **A user-asked notification test sends despite quiet hours — and says so (#92).** The alternative (respecting the gate silently) makes the test useless exactly when the user is debugging silence. The balloon is sent, the suppression that AUTOMATIC notifications are under is named in the result line, and the send is logged. Automatic surfaces keep honoring the S4 gate unchanged.
- **The bundle screenshot renders the window's own visual tree — never the screen (#95).** `RenderTargetBitmap` over the main window makes other windows and the desktop physically unable to appear; the trade-off (documented in KNOWN_LIMITATIONS) is that the rendered page area is included exactly as displayed, conversation text and all — hence opt-in, off by default, previewed with the warning before it can enter the bundle, and unavailable while the app is locked or the window hidden.
- **Help is a shipped file + a Core catalog, the What's New pattern (#91).** Page bodies live in `Help.md` beside the exe; `HelpCatalog` (ids, titles, symptom keywords, the in-app action each page offers) lives in Core, and a test pins the file's sections to the catalog exactly — a page can't be added to one and forgotten in the other. Help actions route into existing surfaces (Settings at a section via the settings-window's own restore-scroll, Diagnostics, the log viewer) rather than growing help-specific duplicates.
- **About became a window because its facts outgrew a MessageBox (#94).** The S9 channel, runtime versions, and licenses need copyable, complete text; LICENSE and THIRD-PARTY-NOTICES.txt now ship beside the exe (the notices state facts + license names — WebView2 SDK © Microsoft, MIT; .NET © .NET Foundation and Contributors, MIT; the Evergreen Runtime is Microsoft's separately-serviced component — rather than reproducing third-party license texts wholesale).

## 2026-10-24 — v0.13.0 Slice 9: updates, installer & distribution (items 81–88)

- **The update check reads the releases LIST, not /latest (#88 forces it).** GitHub's `/latest` endpoint structurally excludes pre-releases, so an opt-in pre-release channel can't be built on it. The check now fetches `releases?per_page=20` (still one quiet request) and Core's `ReleaseSelection.SelectNewest` applies the channel: stable = non-prerelease releases with suffix-free tags (the flag and the tag must agree — either one marks a pre-release); pre-release channel = newest base version wins, stable beating a pre-release at the same base. Selection never offers a downgrade; the one sideways offer is deliberate — a running pre-release whose base version shipped as stable is offered that stable (switching back to Stable must have somewhere to go). `UpdateInfo.IsNewer`/`ParseLatestReleaseJson` remain for their existing tests; new logic lives in `Updates.cs`.
- **An installer runs only after its hash matches the release's own sums (#81).** The updater downloads the installer to a `.partial` file, fetches `SHA256SUMS.txt` from the same release, and compares SHA-256 before the file is even renamed into place. Missing sums asset, missing entry, or mismatch → the file is deleted and the user gets a plain explanation; there is no "install anyway" path. That makes `SHA256SUMS.txt` a hard release requirement from v1.0.0 on (the checklist pins it) — the v0.5.0 release already published one. Progress reuses the S2 EWMA `DownloadRateSampler` and Core formats percent + speed + ETA; the download is an app-level HttpClient job, NOT a WebView2 download (it must work when the page is suspended/locked-adjacent and must never enter the downloads history — its addresses are release-asset URLs, logged by file name only).
- **What's New is a shipped file, guarded against drift (#82).** Options were a build-time generation step from CHANGELOG.md (more machinery in the csproj, and a step that can fail silently on a dev machine) or a checked-in `WhatsNew.md` copied to the output. Chosen: the checked-in file, regenerated from the changelog at release time (a checklist step), with a Core test that extracts the csproj version's section from BOTH files and fails unless they're identical — drift can't ship quietly. Fresh installs record the version without showing (no "new" exists for them), the window never precedes the app-lock gate, and a missing section records the version anyway so a packaging slip can't nag every launch.
- **Rollback keeps exactly one previous installer, and its coverage is stated plainly (#84).** The updater keeps the installer it downloaded in an `updates\current` slot; when the NEXT verified update is about to install, that installer rotates into `updates\previous` and becomes the Diagnostics **Reinstall previous version** offer (file must exist and match this PC's architecture — a copied settings file can't conjure an offer). Consequences, documented rather than smoothed over: the first updater-reached version has no rollback (nothing was kept before it), and versions installed from the website/zip are outside the chain. A rollback does not rotate the records back — the newer installer stays in `current`, so re-updating re-offers the same rollback. Rotation failures never block an install the user already approved.
- **winget is prepared, not submitted (#85).** `packaging/winget/` holds a complete 1.6.0-schema manifest set for v0.5.0 (the latest published release) with the real installer URLs and hashes taken from that release's verified `SHA256SUMS.txt`, plus the submission steps. Submitting to microsoft/winget-pkgs is an external publication under the maintainer's identity — it waits for SEAN's explicit go-ahead, and the README there says `winget install MuseDesktop` is not live until then. The per-release manifest bump is a checklist step from now on.
- **The installer audit found one real gap (#86).** The folder choice the item asked for already existed (MUI directory page, per-user, `InstallDirRegKey` reuses the recorded folder on upgrade), and the desktop shortcut already existed as an optional Components section, off by default. What was missing: the shortcut choice wasn't remembered, so an upgrade's Components page showed it unchecked even when the user had chosen it (the existing shortcut file survived, but the page lied). The script now records the choice (`HKCU\Software\MuseDesktop\DesktopShortcut`) in a final always-run section and pre-selects it in `.onInit` — which must be defined AFTER the sections, because NSIS section constants resolve at declaration. Compile-checked with makensis against a dummy stage.
- **Signing is a ready switch, not a certificate (#87).** SEAN's decision stands: no certificate has been bought and this slice doesn't obtain or fake one. `.github/workflows/sign-release.yml` is `workflow_dispatch`-only and skips itself unless the repo variable `SIGNING_ENABLED` is `true`; enabling = buy an OV (or EV) code-signing certificate from a public CA, add two secrets (`SIGNING_CERT_PFX` base64 + `SIGNING_CERT_PASSWORD`), flip the variable. It signs the two installer EXEs and regenerates `SHA256SUMS.txt` (signing changes the bytes, so the sums must follow). Known scope limit, stated in the checklist: the workflow signs the installers, not the `MuseDesktop.exe` inside the zips — SmartScreen's prompt appears on the installer first run, which is the friction that matters; exe signing is a follow-up if a cert lands.
- **Update state records are not preferences.** Channel/frequency/snooze/What's-New-opt-out reset with the other preferences; `LastUpdateCheckUtc`, `LastSeenVersion`, and the kept/previous installer records survive a reset (a reset must not strand a rollback or re-show old notes) — the same state-vs-preference line S7/S8 drew, pinned by tests.

## 2026-10-24 — v0.12.0 Slice 8: performance, reliability & recovery (items 71–80)

- **One recovery coordinator owns every automatic reload (#71/#76).** Core's `RecoveryCoordinator` replaced S1's `_autoRetried` flag: renderer exits map to a page reload, browser-process exits to a full web-view recreate, and connectivity signals (network address/availability change, resume from sleep) map to a reload only when the page sits in a failed state. All three share ONE budget — one automatic recovery per incident, refilled only by a successful load — so crash-then-offline-then-wake can never stack into a reload loop. Everything else (GPU/utility process restarts, `RenderProcessUnresponsive`) maps to *None*: WebView2 restarts its helpers itself, and unresponsiveness belongs to the watchdog (#80), which never auto-reloads.
- **Browser-exit recovery recreates the WPF controls, not just the environment (#71).** A WebView2 WPF control is bound to its dead environment; the honest fix is disposing both `WebView2` controls (main + the hidden S2 retry view), constructing fresh ones into the same layout hosts, and re-running the normal init with the last page as the restore URL. The fields are the window's only references, so the rest of the shell is untouched. If recreation itself throws, the failure overlay shows — recovery still ends at a human decision, never a loop.
- **The data cap deletes by allowlist, and the protected set is the point (#75).** `CacheCleanup` can only ever name folders from `DisposableFolderNames` (Cache, Code Cache, GPUCache, GrShaderCache, ShaderCache, DawnCache, GraphiteDawnCache) and explicitly refuses everything in `ProtectedFolderNames` (Network, Local Storage, Session Storage, IndexedDB, WebStorage, Service Worker, Sessions, shared_proto_db, Sync Data) — unknown folders are skipped, not guessed at. Planning is pure Core over measured sizes, oldest-first (least-recently-written first), and tests pin that a plan can never contain a protected name, even at target zero. Cleanup is stamped onto the profile and surfaced in two Settings places; silence was treated as a defect.
- **The watchdog asks, never acts (#80).** A 15 s `ExecuteScriptAsync("1")` ping with a 5 s timeout; two consecutive misses raise a non-modal banner with Reload / Wait (Wait snoozes 2 minutes). It suspends while tray-suspended (a sleeping renderer can't answer — that's not a hang), while locked, after the mic was granted this session (S4's voice heuristic), and while the page plays audio. A script ping can fail during heavy legitimate work — the banner says exactly what was detected and the user decides.
- **Proxy is read, never set (#77).** Audit result: no code anywhere in the app sets WebView2 proxy arguments (`AdditionalBrowserArguments` is never used) — WebView2 follows the per-user WinINET settings, which Diagnostics merely reads (`ProxyEnable`/`ProxyServer`/`AutoConfigURL`). Server strings are sanitized in Core: any `user:pass@` userinfo is stripped before display or logging, so a credential embedded in a proxy string can never leak into the UI or the log.
- **Runtime floor is 120.0, dated and conservative (#78).** `RuntimeHealth.MinimumVersion` = 120.0.0.0 (comment dated 2026-10-24): the first Chromium-120-era Evergreen runtime, old enough that anything below it is genuinely ancient, new enough to matter. The check distinguishes missing / outdated / fixed-version-folder-present / OK; the fixed-version note exists because the app ships Evergreen (`browserExecutableFolder: null`) — a `FixedVersionRuntime*` folder beside the exe silently changes that contract, so it's surfaced rather than honored.
- **Safe mode narrows behavior, never security (#72).** `--safe-mode` (or Shift at launch) skips last-page restore (lands on Home) and the automatic update check; the app lock gate runs exactly as normal — a recovery mode that bypassed the lock would be a lock bypass. Shift detection is best-effort convenience; the flag is the documented contract. The reset wizard reuses S5's backup-first reset and S7's granular clear rather than duplicating them, and blocks its settings step when the backup write fails (the S5 rule).
- **Backups rotate per kind, beside settings (#79).** `auto-{settings|downloads}-{yyyyMMdd-HHmmss}.json` in `RootDir/backups`, keep 5 per kind, at most one automatic backup per kind per day (checked at startup and on settings saves, which are frequent). Names are validated by Core's parser — the S5 reset backups (`settings-backup-*`) live in the same root but are a different family and are never pruned by rotation. Restoring settings goes through `SettingsStore.TryImport` + the window's own copy-in, identical checks to Import.

## 2026-10-24 — v0.11.0 Slice 7: privacy & security (items 61–70)

- **WebView2 APIs were verified against the pinned SDK (1.0.4258.31) before use — one named API does not exist.** Present and used: `CoreWebView2Profile.ClearBrowsingDataAsync(CoreWebView2BrowsingDataKinds)` (Cookies / DiskCache / CacheStorage / AllProfile), `CookieManager.GetCookiesAsync` (null URI = all cookies in the profile), `CoreWebView2Settings.IsPasswordAutosaveEnabled` / `IsGeneralAutofillEnabled`, `CoreWebView2.ServerCertificateErrorDetected` (+ `ClearServerCertificateErrorActionsAsync`), and `CoreWebView2Environment.BrowserVersionString`. **Absent: `CoreWebView2Profile.GetPermissionsAsync`** — the enumeration API the #62 sketch named doesn't exist in the pinned SDK. The fallback is better anyway: `GetNonDefaultPermissionSettingsAsync()` **does** exist and returns exactly the saved (non-default) choices with kind + origin + state, which is what a permissions manager should list; revocation/re-grant goes through `SetPermissionStateAsync` (Allow / Deny / Default = forget). Also present but not needed: a time-range `ClearBrowsingDataAsync(kinds, start, end)` overload — the slice's choices don't include time ranges, so it stays unused rather than growing a UI nobody asked for.
- **Non-active profiles are reached through a throwaway environment, never by file surgery (#61/#63).** Clearing or counting cookies for a profile that isn't running creates a temporary `CoreWebView2Environment` over that profile's data folder plus an invisible controller (against the main window's handle, closed immediately after). The folders are per-profile and no other process holds them, so this is the SDK's own route to the same profile object the live path uses — one code path for kinds/counts, honest per-profile failure reporting, and no hand-deleting of cookie stores behind WebView2's back.
- **#64's design is SEAN's call, taken mid-slice: an in-app password/PIN, not Windows Hello.** The item was originally held for that decision. Consequences: the credential is an app-level secret, stored as a salted PBKDF2-HMAC-SHA256 record (210,000 iterations, 16-byte random salt — the same primitives and cost as #65's encrypted export) in three settings fields (salt, hash, iterations). 4–64 characters, digits or a passphrase; the UI recommends 6+. Setting/changing it from Settings asks for the current credential first when one exists, so a walk-up user at an unattended unlocked session can't swap it.
- **The lock is fail-open by construction, and recovery is a file delete (#64).** An enabled lock whose record is missing/malformed is disabled by `AppSettings.Sanitized()` (and logged via a `[JsonIgnore]` repair flag the shell checks after load) — a damaged or hand-edited settings file can never brick the app. The documented forgotten-password recovery is deleting `settings.json` from the data folder: the lock record lives there, so the lock goes with it; settings return to defaults (including the profile LIST), but the default profile's sign-in survives because cookies live in the separate WebView2 profile folders — the Settings text and KNOWN_LIMITATIONS say exactly this, and a Core test loads a corrupt-record settings file to prove it comes back unlocked.
- **Pre-unlock gating is two-layered (#64).** For a launch that will show a window, App runs a modal `LockWindow` **before MainWindow is constructed** — WebView2 doesn't exist yet, so no page can render or navigate pre-unlock, and closing the gate shuts the app down (no locked zombie). For a hidden tray launch, showing a password modal on autostart would be a surprise, so MainWindow is constructed in locked mode instead: `OnLoaded` defers `InitWebViewAsync` (and the update check) until unlock, and every show path (`ShowFromTray`, tray Settings/Downloads delegates) routes to the lock screen. Mid-session locks gate surfaces, not the engine: the window hides, all other windows (secondary, Downloads, Settings) close, the tray tooltip/menu go plain and content-naming items disable, the download-complete balloon is suppressed — but downloads in flight finish. One `AppLockThrottle` per window session is shared by every lock screen, so closing/reopening one doesn't reset the wrong-try count; the throttle itself (5 fails → 30 s cooldown, success resets, no wipe/lockout-forever) is a Core state machine on caller-supplied time.
- **What the lock does NOT do is stated everywhere it appears (#64).** It stops casual access to the open app. It does not encrypt profile data on disk (the WebView2 folders remain ordinary DPAPI-protected-per-user data), and it is not a sign-out. Settings text, CHANGELOG, and KNOWN_LIMITATIONS all say so in those words.
- **Privacy counters live outside settings (#67).** `privacy-stats.json` next to settings: counts keyed category|kind|host (host-only — `PrivacyStats.CleanHost` rejects anything carrying a path/query into the counter), a capped recent-denials list (20), one since-date, a 200-row cap. Separate file on purpose: counters are this-PC facts and must not ride a settings export to another machine. The hooks are the three existing block sites in MainWindow (blocked navigation, blocked new window, denied permission); the secondary window logs its own blocks but doesn't count them (it's a transient viewer with no stats handle — its blocks still land in the log and in #66's audit).
- **Certificate errors: the app previously had NO handler (#69).** Nothing subscribed to `ServerCertificateErrorDetected`, so WebView2's default applied — its built-in error page (which the app separately disables for navigation errors and replaces with its own overlay) carried certificate failures. Now: a deferral-based modal asks every time, defaulting to Go back; "Continue anyway" sets WebView2's `AlwaysAllow` for that host and is mirrored in an in-memory per-host map — **session-only, never persisted**, so a restart forgets it; the choice is logged (host only). The ⋯ menu's Connection security dialog shows the current host/HTTPS state, certificate subject/issuer/validity on HTTPS, the runtime version, and can forget the session's overrides (`ClearServerCertificateErrorActionsAsync` + clearing the map).
- **Cookie values are never read into UI text (#63).** `GetCookiesAsync` returns values; the gateway's summarizer touches only `Domain` and counts. The site-data rows show totals + distinct-domain counts; the per-domain breakdown exists in the gateway result but the shipped UI doesn't display even names today — counts only. This is a deliberate under-use of the API.
- **The permissions manager is scoped to the running profile, and says so (#62).** The live profile is the only one whose choices can change under a running app; other profiles' choices become visible when that profile runs. The section labels itself "profile MuseDesktop is currently running" rather than implying a global list. Recent denials come from #67's stats (this PC, all profiles — also labeled).
- **Autofill flags are profile-shared in WebView2 (#68).** The SDK documents `IsPasswordAutosaveEnabled`/`IsGeneralAutofillEnabled` as one shared value per profile ("changing one changes the other" across a profile's web views), so applying at the main view's init — and live on Settings OK — genuinely covers secondary windows too. Before this slice the shell hardcoded both to true at init; now they come from settings, defaulting to true = WebView2's own defaults, so no existing user sees a behavior change unless they flip the toggles.
- **Reset-all-settings deliberately does NOT touch the app lock (#64).** `SettingsReset.ApplyDefaults` restores preferences; a credential is not a preference, and a reset silently stripping a security control would be a nasty surprise. Removal lives in the Privacy section, behind an explicit confirm (and, for change, the current credential).
- **The encrypted export envelope is app-detectable and versioned (#65).** Magic first line `MUSEDESKTOP-SETTINGS-ENCRYPTED`, then JSON {version, iterations, salt, nonce, tag, data}: PBKDF2-HMAC-SHA256 (210,000 iterations, 16-byte salt) → AES-256-GCM (12-byte nonce, 16-byte tag), .NET built-ins only. Import distinguishes three failures in plain words — not encrypted / damaged envelope / wrong password or altered data (GCM auth failure) — and the password prompt is never shown for a plain file. The lock hash riding plain exports is disclosed in the export dialog itself when a lock is set.

## 2026-10-24 — v0.10.0 Slice 6: accessibility, keyboard & focus (items 51–60)

- **There is no global hotkey, so #53 remaps only what exists (#52/#53).** Checked the whole shell before designing: no `RegisterHotKey` anywhere; show/hide is the tray icon (click / double-click) plus the single-instance wake event. The item's premise ("remap the global show/hide hotkey") names a feature the app never had, and inventing a new global hotkey was out of scope — so the catalog's `Global` scope exists but is deliberately empty, and the remappable set is the three in-app actions: Settings (Ctrl+, — a real binding since v0.2.0), Downloads and Home, which **had no keyboard gesture at all** before this slice and gained defaults (Ctrl+Shift+D, Alt+Home) precisely so there is something honest to remap. Everything else the shell binds stays in the catalog as fixed. If a global hotkey is ever added, it lands in the catalog as a Global entry and this model already fits it.
- **One catalog, three consumers (#52/#53).** `ShortcutCatalog` in Core is the single source of truth: the Shortcuts window renders it (with effective gestures), the Settings editor edits its remappable subset, and the main window dispatches remappable actions by comparing the pressed gesture against `ShortcutBindings.EffectiveGesture`. Overrides live in settings as action-id → canonical gesture text ("Ctrl+Shift+D"). Sanitizing uses final-state semantics (catalog order, first claim wins; an override may take another action's default only when that action has itself moved) so a settings file can never encode an ambiguity the dispatcher would have to guess at; equality with a fixed gesture is a conflict even in storage. Overrides require Ctrl or Alt — a bare key would fire while typing. The main window checks remappable gestures BEFORE the fixed Ctrl block, which is safe precisely because sanitize/TrySet guarantee an override can never equal a fixed gesture.
- **Downloads and Home defaults were chosen to be collision-free and mnemonic.** Ctrl+Shift+D (Downloads) and Alt+Home (the browser-convention Home key, matching the existing Alt+Left/Right navigation family). Neither collides with any existing binding or with Chromium conventions the page relies on; both are in the gesture-eligible key set (Core whitelists letters/digits/F-keys/nav/OEM keys — Escape is deliberately NOT gesture-eligible, since Esc is the universal cancel and the find/fullscreen handler owns it).
- **Reduce motion gates the flash, and that's the whole surface (#55).** The shell has NO storyboard/transition animations — verified by reading the shell: every state change is an instant Visibility/brush swap (focus mode, menus, overlays). The one motion-like effect the shell produces is the S4 taskbar attention flash (`FlashWindowEx` is an OS effect), so `MotionPolicy` gates exactly that, with a log line when it suppresses. The Windows side reads SPI_GETCLIENTAREAANIMATION via SystemParametersInfo (the documented query behind the Settings "Animation effects" toggle). Page motion is Chromium's business: the web view already honors Windows' setting through prefers-reduced-motion, and the app does not inject anything into the page. Claiming more surface than this would be inventing it.
- **High Contrast = SystemColors, applied as overrides after the palette (#51).** When `SystemParameters.HighContrast` is on, ThemeManager repaints every shell token from the system role that matches it (Window/WindowText for surfaces and text, Control for raised, GrayText for faint, Highlight/HighlightText for the accent/fill/text-on-accent triple). This runs inside the same in-place brush mutation S5 established, so open windows repaint; and App now re-applies the theme on EVERY UserPreferenceChanged (S5 re-applied only in Follow-Windows mode) so an HC toggle lands live. Four hard-coded `Foreground="White"` accent buttons (reload overlay, Settings OK, Downloads Open, wizard Save) moved to the new `AccentTextBrush` token so HC can pair Highlight with HighlightText. What code inspection can verify: the palette mapping exists, is complete over the token set, and the title-bar/DWM path is unchanged. What it cannot: that every pixel is legible in all four Windows HC themes — that is the on-machine pass in RELEASE_CHECKLIST.
- **Focus visuals: one explicit style, applied implicitly + inside local styles (#51).** App.xaml defines `ShellFocusVisual` (a 2px accent border template) and implicit FocusVisualStyle setters for the interactive control types. WPF's default focus visual is theme-dependent and effectively invisible on this dark shell; worse, SettingsWindow's window-local CheckBox/RadioButton styles silently dropped any inherited focus visual, so they now set it explicitly too. Focus order needed no surgery: every window's XAML declaration order IS the logical tab order (verified by reading each window top to bottom during the pass).
- **The #59 audit is a test, scoped to XAML-declared controls.** `XamlAccessibilityAuditTests` parses every `src/MuseDesktop/*.xaml`, walks elements skipping DataTemplate/ItemTemplate subtrees (their content is data, not controls), and fails any Button/MenuItem/TextBox/ComboBox/CheckBox/RadioButton/Hyperlink/ToggleButton/ListBox with no AutomationProperties.Name, ToolTip, Content, Header, or inner text. The repo root is located by walking up from the test ASSEMBLY's location (AppContext.BaseDirectory points at the console runner under our gate — a real bug caught while writing it). Controls created in code (Settings' shortcut rows, toolbar editor checkboxes) are outside its reach by construction — they set Content/ToolTip in code, and the audit's scope note says so. On its first run it flagged exactly four controls — Downloads' two ListBoxes and Settings' two zoom ComboBoxes — all fixed in this slice.
- **Placement clamping is per-monitor-rect math in Core (#60).** The old restore check used one virtual-screen bounding box, which passes a window stranded on a disconnected monitor whenever the box still covers the point, and knows nothing of per-monitor scale. Now: the shell enumerates monitors (EnumDisplayMonitors + GetMonitorInfo), converts each PHYSICAL rect to DIPs at that monitor's own GetDpiForMonitor scale, and Core's `PlacementClamp` keeps the window if ≥80×40 DIPs of it show on any single monitor (the old minimum-visible rule), else fits it into the primary. Any enumeration failure falls back to the old virtual-screen single-"monitor" behavior. The manifest's PerMonitorV2 declaration was previously only a comment claiming the .NET default; it is now explicit (`<dpiAware>` + `<dpiAwareness>`), and the WinForms analyzer's WFO0003 objection is suppressed in the shell project with a comment — WPF reads DPI awareness from the manifest, not from the WinForms-only SetHighDpiMode API.
- **Zoom steps: finer near 100%, extremes behind a setting (#57).** The standard table now steps 5% between 75% and 125% (25-point jumps at the ends), because eyes notice a 10% jump at reading size and don't at 50%. The extended table inserts 25%/33% below and 250–500% above, and exists only when the setting is on — clamping, per-profile zoom sanitizing, and Settings' combo lists all take the same flag, so a 300% zoom can never be stored while the range is off (it clamps to 200% at load instead of stranding the page somewhere the UI can't represent). Two pre-S6 Core test expectations changed with the table (step from 100% is now 105%, not 110%) — the table IS the behavior the item asked for.

## 2026-10-24 — v0.9.0 Slice 5: settings, appearance & personalization (items 41–50)

- **Settings search is section-level (#41), because Settings is one scrolling window, not tabs.** The window's seven sections (Behavior, Tray & notifications, Account profiles, Appearance & toolbar, Zoom, Downloads, Data) are the unit: matching sections stay visible with highlighted headers, the rest collapse, the first match scrolls into view. The word→section index lives in Core (`SettingsSearch`) with tests pinning that real queries ("portable", "collision", "wizard") land in the section that actually holds the setting — an index in the shell would drift silently. Row-level filtering was rejected: hiding individual rows inside a section would tear apart grouped controls (the radio + URL box of #47, the quiet-hours pair) and the write-through profile controls assume their section's controls all exist. A side effect worth having: item #48's "remember last tab" becomes "remember last section" — the section at the top of the viewport when OK is chosen, plus the window size (the window is resizable now; it was fixed-size before).
- **Theme application mutates the shared brushes (#43); it does not swap resource dictionaries.** Every shell window paints from the App.xaml brush objects via StaticResource, so `ThemeManager` changes those brushes' `Color` in place (Dark / Light / FollowSystem, the last read from `AppsUseLightTheme` at startup and on `UserPreferenceChanged`). Already-open windows repaint with no XAML changes anywhere; windows opened later parse against the same objects. The palettes are Core hex records (`ShellPalettes`) with WCAG ratios pinned by tests: Text and Muted ≥ 4.5:1 on every surface of their theme; Faint is de-emphasis only, ≥ 3:1, and the docs say so rather than pretending otherwise. The Muse page is untouched, and the web view's pre-load background follows the palette so a light shell doesn't flash black. Title bars follow via the same DWM immersive-dark attribute the app already used.
- **Accents have two variants each (#44) — one hex cannot do this job.** A single accent would need ≥ 4.5:1 as text on a near-black background AND on a near-white one AND under white button text; the luminance bounds contradict each other (the family red #E50914 measures 4.10:1 on the dark background — it was always decoration-grade there, never text-grade). So `AccentPalette` stores a brighter dark-shell variant (text/decoration on dark) and a deeper light-shell variant (text on light, and the FILL for accent buttons in both themes, where white-on-fill is ≥ 4.5:1 — pinned per accent by tests). Call sites that fill a button with white text use the new `AccentFillBrush`; text call sites keep `AccentBrush`. Profile colors (#24) are a separate palette and are not conflated with this one.
- **Toolbar layout is (order, hidden), not a single visible-list (#45).** Settings store every known button id in display order plus a hidden set. That split is what lets sanitize append a future new button at its canonical position instead of mistaking "absent" for "user hid it". Back can never be hidden (the toolbar must always offer navigation) and the ⋯ menu is not a layout item at all — fixed, last, always available, since it is the only route to Settings/Downloads. The shell does not rebuild buttons: the XAML declares them once with handlers/styles, and `ApplyToolbarLayout` only re-parents them into the strips in the saved order, omitting hidden ones. Reorder in Settings moves within the combined list; the left/right grouping is a property of each button, not something the user can break.
- **Shell text size scales locally-set font sizes from remembered design values (#46).** `ShellTextScaling` walks a window's logical tree, multiplies each locally-set FontSize by the factor (100/125/150, Core-snapped), and remembers the design size per element so re-applying never compounds; the window's inherited base size scales too. Reached: main window, Settings, Downloads, the wizard, and the ⋯ menu (applied explicitly on open — pop-ups live outside the window tree). NOT reached, stated in KNOWN_LIMITATIONS: the WinForms tray menu (Windows draws its font) and the second window (it has no shell text of its own beyond the title bar). No Viewbox scaling — text stays text.
- **The start-page choice is a 3-way mode on the profile (#47), migrating the v0.4.0 bool.** `AccountProfile.StartPage` (LastPage / Home / Custom) extends `StartAtHome`; `EnsureValid` migrates a pre-v0.9.0 file's bool into the mode on first load and keeps the bool rewritten from the mode thereafter, so a downgrade still reads the choice correctly. Validation is launch-time (`StartPagePolicy`): a custom URL must be an absolute HTTPS URL on an in-app host passing the ordinary navigation policy; invalid → Home + a log line with the value redacted. The stored string is only trimmed and length-capped — validation at use, not at save, so a typo is fixable in place and the fallback behavior is one tested code path.
- **Reset-all is preference-only, and the backup is a precondition (#42).** `SettingsReset.ApplyDefaults` copies defaults into every preference field while preserving identity/session state: profiles, the active id, per-profile last pages, window placements, the deferred-deletion queue, and the Settings-window memory. Resetting must never sign anyone out of an account or orphan a profile folder — profile removal is its own explicit, data-deleting action. FirstRunCompleted IS reset (a reset returns the app to first-run state, wizard included). In the shell the flow is: confirm → export the pre-reset settings to `settings-backup-<timestamp>.json` in the settings folder → only then apply. If the backup write fails, the reset does not happen; the note in the window says so. Import undoes a reset completely.
- **Portable mode is a marker file, not a setting (#49).** A settings-held "portable" flag would be circular (the settings file's location is what it decides). `portable.txt` beside the exe → settings/download-history/logs root becomes `<exe dir>\data`, resolved in Core (`SettingsLocation`) and consumed through the existing `AppPaths` properties, so no caller changed. Nothing migrates automatically in either direction: entering portable mode starts fresh, removing the marker returns to the installed data untouched — silent data movement is exactly what a portable user carrying a USB stick does not want to discover later. Scope limit, stated plainly: the **WebView2 sign-in profiles stay in %LOCALAPPDATA%** in this version — #49 as specified covers settings + download history; moving the (large, lock-sensitive) browser profile is a separate decision for a later slice.
- **The first-run wizard edits a clone and never persists itself (#50).** One window, the four highest-regret defaults (close-to-tray, start-with-Windows, downloads folder, update checks), pre-filled with current values. App shows it once — when `FirstRunCompleted` is false — and ANY exit (Save, Skip, the X) records completion: a wizard that nags twice has failed its only job. A first run also never starts hidden (the wizard needs a visible owner). One subtlety: pre-v0.9.0 settings files have no such flag, so an upgrader's file would read as "first run" — App distinguishes by the settings schema marker (pre-v0.9.0 files load as schema < 2): an existing file from an older build is an upgrade, not a first run, and is silently marked completed; `SettingsReset` deliberately preserves SchemaVersion so a post-reset launch (schema 2, flag false) still re-offers the wizard as designed. Re-running from Settings edits the Settings window's working clone and refreshes its controls, so a wizard change can't fight the clone/OK flow. Two name collisions worth noting for future slices: .NET 10 WPF has its own experimental `System.Windows.ThemeMode`, so shell code fully qualifies `MuseDesktop.Core.ThemeMode`; and WinForms global usings force fully-qualified media types in the new shell files, as elsewhere.

## 2026-10-24 — v0.8.0 Slice 4: tray, notifications & presence (items 31–40)

- **Attention signal (#31): the document title's leading "(N)" prefix, and nothing else.** Muse's page offers the app no unread API. The one defensible signal is the widespread title convention ("(3) Muse" = 3 unread) that Gmail/Slack/Discord use. The Core parser (`AttentionSignal.Parse`) accepts exactly that shape — leading parentheses, digits only, ≤4 digits, followed by whitespace or end-of-title — and returns None for everything else, including "(0)", "(Official) Muse", and counts elsewhere in the title. Muse's favicon badge was rejected as a signal: WebView2's `FaviconChanged` hands over an image, and pixel-guessing a badge out of it is exactly the kind of inference this feature forbids. Consequence, accepted knowingly: if muse.ai does not use the "(N)" convention, the badge never appears. That is the correct failure mode for a "never guess" feature. The taskbar mirror uses WPF `TaskbarItemInfo.Overlay`; the tray badge is painted onto the icon (top-right; profile dot bottom-left — the split layout is a Core plan, `TrayIconPlanner`, the pixels are the shell's `TrayIconRenderer`).

## 2026-10-24 — v0.7.0 Slice 3: profiles & accounts (items 23–30)

- **Shortcut mechanism (#23): WScript.Shell late-bound COM, and --profile persists like a switch.** The .lnk is written through `Type.GetTypeFromProgID("WScript.Shell")` + `Activator` (the dynamic COM pattern TaskbarProgress already uses), not IShellLink P/Invoke — a dozen lines, no vtable declarations to get wrong, failure-tolerant with a plain error in Settings. Stated limit: while the app is already running, single-instance still just wakes the running window — a shortcut does not switch a running instance.

- **Deferred folder deletion (#28): a persisted id queue, retried pre-environment.** Settings stores `PendingProfileFolderDeletions`. At startup — after the single-instance check, before the main window exists, hence before any WebView2 environment can hold a folder open — each queued folder delete is retried, never for the profile being launched. Sanitization is the safety net: the list is deduped, valid ids only, capped, and **any id naming a live profile is dropped**, so a re-created profile can never have its folder deleted out from under it.

Everything session-adjacent is excluded by construction: LastUsedUtc starts null, and last pages live in `LastUrlByProfile` under the profile's own id, so a new id has none. Tests pin both directions.

Unknown keys sanitize to none, so settings files can't invent colors and the palette can evolve without breaking old files. ## 2026-10-24 — v0.6.0 Slice 2: downloads (items 13–22)

- **Pause/resume API finding (#14): PRESENT in the pinned SDK, no fallback or fake needed.** The 1.0.4258.31 package's Core XML documents `CoreWebView2DownloadOperation.Pause()`, `.Resume()`, and `.CanResume`, plus the `UserPaused` interrupt reason. Semantics that shaped the tracker: pausing moves the operation to `Interrupted` with reason `UserPaused` — so "interrupted" is not synonymous with "failed". The tracker treats `UserPaused` as a first-class Paused state (stays tracked, no history record, Resume offered per `CanResume`), `UserCanceled` as cancelled (no record), and every other interrupt reason as a failure. (The SDK's own Pause summary text says "UserCanceled" — that contradicts its `UserPaused` enum member and the documented resume flow; the enum is what the code keys on, and the S2 on-machine pass must confirm the reason value in practice.)
- **Retry mechanism (#15): a hidden WebView2 on the same environment, in-session only — and why nothing stronger exists.** Download source URLs are never persisted (standing rule), so after a failure the URI survives only in the shell's memory (`SessionFailedDownload`). Retry creates a 1×1 hidden WebView2 from the main window's existing `CoreWebView2Environment` (same profile/sign-in), wires its `DownloadStarting` to the *same* handler the main view uses — so destination policy (effective folder, ask-where-to-save, collision handling) is identical — and navigates it to the remembered URI. If the server answers with a file, the handler takes the operation over and the tracker follows it like any download. Honest limits: if the server instead returns a page (expired signed link, interstitial), that page loads invisibly in the hidden view and no download starts — a manual re-download from the chat is then the route, and the status bar says the retry was started, never that it succeeded. There is no WebView2 "restart this operation from a URL" API; re-navigation is the only real mechanism, and fabricating a resume of the dead operation was rejected.
- **Failure records in history (#16): a State field, defaulting to Completed.** Old history files have no state field and deserialize as Completed — which is exactly what every pre-v0.6.0 record was. Failed records store the interrupt-reason *name* (e.g. `NetworkFailed`), size-received, and time; never a URL. User-cancelled downloads are deliberately NOT recorded: the user already knows they cancelled, and a history full of cancellations would drown the failures the filter exists to find.
- **The multi-download manager lives in the existing Downloads window (#13),** not a new window or popover: an Active list on top (polled at 750 ms while open, selection preserved by id) over the history list. The status bar keeps the pre-S2 `ProgressStatus` wording byte-for-byte for a single download — the only intentional wording change in the slice is the speed appended to the right-hand detail (#22), implemented as a new overload so the pinned v0.4.0 tests pass unmodified. With several downloads the status bar switches to a Core-computed aggregate; per-file detail lives in the manager.
- **Taskbar progress (#19): ITaskbarList3 via a vtable-prefix interface.** Only the interface prefix through `SetProgressState` is declared (COM slots are positional), the coclass is activated through `Type.GetTypeFromCLSID` + `Activator` (a direct cast from a ComImport coclass doesn't compile), and every call is wrapped so a taskbar failure degrades to a log line. Failure latches the Error state in the main window until the next download starts; a paused-only set shows Paused (yellow).
- **Effective downloads folder (#20) is a Core resolution, not shell branching:** profile override ?? shared folder ?? null, where null deliberately means "leave `ResultFilePath` at WebView2's default" — that's the *system* Downloads folder including when a user has relocated it in Windows, which a hard-coded `%USERPROFILE%\Downloads` would get wrong.
- **Delete-file removes the history entry too (#17).** The alternative (keep a row pointing at a file the user just deleted from inside this window) was rejected as a confusion factory; Clear-history remains the files-untouched route. The confirm dialog states plainly that `File.Delete` is permanent (no Recycle Bin) — if a future slice wants bin semantics it will need a shell API this one deliberately did not fake.

## 2026-10-20 — C# / WPF + WebView2 instead of the usual Rust default

Muse is a website, so the client is a shell around a web view. On Windows the first-party tool for that is Microsoft's WebView2 (Edge/Chromium) with its official .NET SDK: documented APIs for the exact things this app needs — a persistent user-data folder (login session), new-window and navigation events, permission requests, and download operations with progress and ETA.

The Rust alternative (wry/tao) abstracts those away behind a cross-platform API whose surface changes noticeably between minor versions, and exposes downloads/permissions only partially. The concrete advantage — a stable, Microsoft-maintained SDK for the one platform this app targets — outweighs the standing Rust default for this project. Plain logic (URL policy, settings, zoom) lives in a dependency-free `MuseDesktop.Core` library so it stays unit-testable anywhere, and the WPF shell stays thin.

Alternatives considered: Tauri (Rust + WebView2, but a large toolchain/JS build for a single-window shell); Electron (bundles a whole Chromium — hundreds of MB to show one website, and a second browser profile to secure); a PWA shortcut (no tray, no download progress, no link policy — the behaviors that justify a native client at all).

## 2026-10-20 — Framework-dependent publish, Evergreen WebView2

The release is a framework-dependent win-x64 publish (~a few MB) that requires the .NET 8 Desktop Runtime and the Evergreen WebView2 Runtime (preinstalled on Windows 11 / most Windows 10). This keeps downloads small and lets Microsoft service the web engine's security fixes independently of this app. Trade-off: two runtime prerequisites, both detected with a plain-language explanation in-app when missing (WebView2) or by Windows itself (.NET).

## 2026-10-20 — Link and permission policy

- Top-level navigation: any HTTPS page may load (sign-in and connector OAuth flows redirect across providers). HTTP and non-web schemes are refused.
- New-window requests: only Muse and known identity-provider hosts (`muse.ai`, `meta.com`, `facebook.com`, `instagram.com`, `accounts.google.com`, `appleid.apple.com`, `login.microsoftonline.com`, exact host or true subdomain) stay in-app. All other http(s) links open in the user's default browser. Look-alike hosts never match.
- Permissions: auto-grant only `notifications` and `microphone`, only for origin `https://muse.ai`. Everything else is denied and logged. Rationale: notifications are how a long-running agent says "done", and the microphone is Muse's voice input; a desktop client that silently granted camera/geolocation to arbitrary origins would be a liability.

## 2026-10-20 — Downloads handled in the status bar

WebView2's default download flyout is suppressed (`DownloadStarting` → `Handled`) and progress is reported in the app status bar as percent + ETA from the download operation, because that matches how the rest of SEAN's apps report progress and keeps the single-window app self-contained. Files land in the default Downloads folder (WebView2's default path).

## 2026-10-20 — Black/red product-family look

Toolbar and status bar use the family tokens (near-black surfaces `#0B0B0D`/`#141417`, hairline `#2C2C31`, red accent `#E50914`, off-white text), and the Windows title bar is set to immersive dark via `DwmSetWindowAttribute`. The web content itself is Muse's own design and is not restyled — injecting CSS into a third-party app would break with their updates and misrepresent their product.

## 2026-10-20 — Settings format

One JSON file, schema-versioned, written atomically (temp file + replace). A file that fails to parse is copied aside as `settings.json.corrupt-<timestamp>` and defaults are used, so user data is never silently discarded. The WebView2 bootstrapper link used in the missing-runtime message is Microsoft's official fwlink (`https://go.microsoft.com/fwlink/p/?LinkId=2124703`, the Evergreen bootstrapper referenced in Microsoft's WebView2 distribution docs).
